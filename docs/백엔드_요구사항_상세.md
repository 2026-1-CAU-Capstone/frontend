# Jazzify 백엔드 요구사항 상세서

> 이 문서는 `기능명세서.md` §B(BR-1~BR-22)의 **상세 버전**이다.
> 기능명세서의 BR 섹션은 "무엇이 문제인지" 요약이고, 이 문서는 **백엔드가 실제로 무엇을 만들어야 하는지**를
> 요청/응답 계약, 완료 판정 기준, 프론트 연동 지점까지 풀어 쓴다.
>
> - `제안` 표시가 붙은 스키마·경로는 **프론트가 제안하는 안**이며, 백엔드 사정에 맞게 조정 가능하다.
> - `확정` 표시는 프론트가 이미 그 형태로 구현/호출하고 있어 **바꾸면 프론트 수정이 필요한** 부분이다.
> - 각 항목의 "완료 기준"을 만족하면 해당 BR을 닫을 수 있다.

# 🔴 최우선

## BR-5. 익명·폴백 채팅을 백엔드 프록시로 + Anthropic 키 회전
`미해결` · **CRITICAL** · BE

### 지금 무슨 일이 벌어지고 있나
프론트가 어떤 경우(비로그인, 또는 백엔드 장애 폴백)에는 브라우저에서 **Anthropic 서버로 직접** 요청을 보낸다.
그런데 이때 쓰는 API 키가 `VITE_ANTHROPIC_API_KEY` 라는 이름의 환경변수다.

**`VITE_` 로 시작하는 환경변수는 빌드할 때 자바스크립트 파일 안에 글자 그대로 박힌다.**
즉 배포된 사이트의 JS를 열어보면 **키가 그냥 보인다.** iOS 앱(IPA)을 뜯어도 마찬가지다.

### 왜 문제인가 (쉽게)
- 아무나 키를 복사해서 **우리 계정으로 무제한 호출**할 수 있다. 요금은 우리가 낸다.
- 키를 지워도, **이미 배포된 번들에 남아 있는 키는 계속 유효**하다. 그래서 "코드 수정"만으론 못 막는다.
- RAG 호출용 Bearer 토큰도 같은 방식으로 노출됐다면 동일한 문제다.

### 백엔드가 할 일
1. **키를 즉시 폐기하고 새로 발급한다.** (코드 수정보다 이게 먼저다. 이미 유출됐다고 가정)
2. **비로그인 사용자용 채팅 프록시**를 만든다 — 프론트가 Anthropic을 직접 부를 이유를 없앤다.
3. RAG 접근 토큰도 폐기·재발급하고 서버 보관으로 돌린다.

#### 제안 API
```
POST /v1/chat/public/stream        # 인증 불필요, 익명 사용자용
Content-Type: application/json

{
  "message": "이 코드 진행 설명해줘",
  "history": [{ "role": "user", "content": "..." }],
  "useRag": false
}
→ text/plain 스트림 (로그인 채팅과 동일 포맷)
```

**반드시 함께 넣을 것 (없으면 이 엔드포인트가 새로운 과금 구멍이 된다)**
- IP + 세션 기준 **rate limit** (예: 분당 5회, 일 30회)
- 요청당 `max_tokens` 상한
- 남용 감지 시 차단 (동일 IP 폭주, 봇 UA 등)
- 익명 요청은 대화 이력 **저장하지 않음**(또는 짧은 TTL)

### 완료 기준
- [ ] 기존 Anthropic 키가 콘솔에서 **폐기(revoke)** 됨
- [ ] 새 키는 **서버에만** 존재 (`.env`·프론트·번들 어디에도 없음)
- [ ] 프론트에서 `api.anthropic.com` 직접 호출 코드가 제거돼도 모든 채팅이 동작함
- [ ] 익명 프록시에 rate limit이 걸려 있고, 초과 시 429 반환

### 프론트 연동점
- `src/api/claude.ts` (직접 호출 경로) 삭제 가능해짐
- `src/components/layout/RightChatPanel.tsx`, `src/lib/chat/runChatStream.ts` 의 폴백 분기를 새 프록시로 교체
- `.env` 에서 `VITE_ANTHROPIC_API_KEY` 줄 삭제

# 🟠 높음

## BR-1. 긴 답변이 문장 중간에서 끊긴다
`미해결` · HIGH · BE / RAG / LLM

### 지금 무슨 일이 벌어지고 있나
RAG 채팅에서 화성 분석처럼 **긴 답변**을 요청하면, 답이 문장 도중에 뚝 끊긴다.
실제 사례: *"E-7은 다이아토닉 iii,"* 에서 스트림이 종료됐다.

### 왜 문제인가 (쉽게)
답변만 잘리는 게 아니다. AI가 그리는 **코드 차트는 보통 답변의 뒤쪽**에 나온다.
그래서 답이 먼저 끊기면 차트 데이터 자체가 전송되지 않는다 →
사용자 눈엔 **"차트가 안 나온다"** 는 별개의 버그처럼 보인다. (차트 버그의 상당수가 사실 이 끊김의 2차 증상이다.)

### 원인 (프론트 아님이 확인됨)
- 프론트 스트림 파서는 서버가 스트림을 닫을 때(`done`)까지 정상적으로 받는다.
- 프론트 폴백 경로는 `max_tokens: 16384` 로 넉넉하다.
- 즉 **끊김은 Spring 백엔드 스트림 경로에서 발생**한다.

의심 두 가지:
1. **토큰 한도** — Spring AI Anthropic 의 `max-tokens` 가 기본값(1024 또는 4096)이라 긴 답이 잘린다.
2. **프록시 타임아웃** — nginx/cloudflared 가 응답을 오래 기다리지 못하고 연결을 끊는다.

### 백엔드가 할 일
```yaml
# application.yml
spring:
  ai:
    anthropic:
      chat:
        options:
          max-tokens: 8192      # 최소 8192, 가능하면 16384
```
```nginx
# nginx (스트리밍 엔드포인트)
proxy_read_timeout 300s;
proxy_buffering off;          # SSE/스트림은 버퍼링 끄기
```
cloudflared 를 쓴다면 스트리밍 타임아웃도 답변 생성 시간 이상으로 올린다.

### 완료 기준
- [ ] 3,000자 이상 답변 + 뒤쪽 차트 블록이 **끝까지** 도착한다
- [ ] 60초 이상 걸리는 응답도 중간에 연결이 끊기지 않는다

### 프론트 완화 (이미 적용됨)
`ChatMessage.tsx` 의 차트 인식 정규식을 관대하게 바꿔, 차트가 앞부분에 완결되면 그린다.
단 **차트 도착 전에 끊기면 프론트가 할 수 있는 게 없다.**

## BR-6. `/v1/auth/me` 응답에 사용자 등급(`role`) 이 없다
`미해결` · HIGH · BE

### 지금 무슨 일이 벌어지고 있나
사이드바의 Admin 메뉴(Chord/Note/Lick/Solo/Editor/YouTube/OMR 관리)는 **관리자만** 보여야 한다.
그런데 `GET /v1/auth/me` 응답에도, 로그인 응답(`TokenResponse`)에도 **등급 필드가 없다.**

### 왜 문제인가 (쉽게)
프론트가 "이 사람이 관리자인가?" 를 물어볼 곳이 없다.
지금은 **아이디가 `admin` 인지 문자열로 임시 판별**하고 있다. 이건 보안이 아니라 임시방편이다.

### 백엔드가 할 일
```jsonc
// GET /v1/auth/me  (제안 — 필드 추가)
{
  "id": 12,
  "username": "benzity",
  "email": "benzity@cau.ac.kr",
  "role": "ADMIN"          // ★ 추가: "ADMIN" | "USER"
}
```
- 가능하면 **로그인 응답에도** `role` 을 포함 (첫 화면부터 바로 반영)
- 관리자 등급을 부여/회수할 수단 필요 (DB 시딩 또는 관리 API)
- ⚠️ **중요**: 프론트의 `role` 은 화면을 숨기는 용도일 뿐이다. **admin 전용 API 는 서버에서 반드시 다시 권한 검사**해야 한다.

### 완료 기준
- [ ] `/v1/auth/me` 가 `role` 을 반환
- [ ] 일반 사용자가 admin API를 직접 호출하면 **403**
- [ ] 프론트에서 아이디 문자열 판별(`username === 'admin'`) 제거 가능

### 프론트 연동점
`api/auth.ts::isAdminUser()` — `role` 이 오면 자동 전환된다. 백엔드만 주면 끝.

## BR-17. 질문 시점에 화성 분석·모호성 계산이 일어나지 않는다 (온라인 분석 API 부재)
`미해결` · HIGH · BE / RAG

### 지금 무슨 일이 벌어지고 있나
Jazzify의 자랑인 "코드마다 역할을 붙여 주는" 화성 분석은 **rule-based 엔진**(파이썬)이 한다.
그런데 이 엔진은 **미리 한 번 돌려놓는 방식(batch)** 으로만 쓰인다.

```
[개발자 PC]  batch.py 실행 → results/<곡>.json
                 ↓ (사람이 직접 복사)
          src/data/<곡>.ts 의 chord.analysis 에 박아넣음
                 ↓
[런타임]   buildChordContext() 가 그 '미리 계산된 값'을 텍스트로 바꿔 백엔드에 보냄
```

즉 **사용자가 질문하는 순간에는 룰엔진이 돌지 않는다.** 모호성 점수(`ambiguity_score`)도 그때 계산되지 않는다.
(근거: `docs/RULE_BASED_BACKEND_INTEGRATION.md` §2.2 — "rule-based가 frontend/RAG runtime에서 호출되지 않음")

### 왜 문제인가 (쉽게)
1. **사용자가 직접 만든 곡은 분석이 안 된다.** 에디터로 입력했거나, iReal에서 가져왔거나, 악보 사진(OMR)으로 만든 코드 진행은 `chord.analysis` 가 비어 있다 → AI에게 넘길 화성 정보가 없다 → 답변이 얕아진다.
2. **모호성 기반 분기(BR-18)의 입력값 자체가 없다.**
3. **운영이 수동이다.** 새 곡을 넣으려면 개발자가 batch 돌리고 결과를 코드에 붙여넣고 배포해야 한다.

### BR-7과 무엇이 다른가
- BR-7 = "OMR이 끝났는데 **코드차트 분석 API가 자동으로 안 돌아간다**"
- BR-17 = "**RAG 질의 시점에** 임의의 코드 진행을 분석할 방법 자체가 없다"
→ 층위가 다르다. 둘 다 필요하다.

### 백엔드가 할 일 — 온라인 화성 분석 API `제안`
```jsonc
POST /v1/analysis/chords
{
  "key": "C",
  "timeSignature": "4/4",
  "chords": [
    { "bar": 1, "beat": 1, "symbol": "Dm7" },
    { "bar": 1, "beat": 3, "symbol": "G7"  },
    { "bar": 2, "beat": 1, "symbol": "Cmaj7" }
  ]
}
```
```jsonc
// 응답 — 프론트의 LeadSheetChordAnalysis 와 같은 모양이면 무수정 연동
{
  "chords": [
    {
      "bar": 1, "beat": 1, "symbol": "Dm7",
      "analysis": {
        "degree": "ii",
        "isDiatonic": true,
        "functions": [{ "function": "SD", "confidence": 1.0 }],
        "groupMemberships": [{ "groupType": "ii-V-I", "role": "ii" }],
        "secondaryDominant": null,
        "modalInterchange": null,
        "ambiguityScore": 0.12          // ★ 모호성 점수
      }
    }
  ]
}
```

운영 요구사항:
- **캐시**: 같은 코드 진행이면 재계산하지 말 것 (진행 해시 → 결과 캐시)
- **온디맨드**: DB에 없는 곡이면 그 자리에서 분석하고 저장
- 기존 batch(Option C)는 그대로 두고 **온디맨드를 얹는** 방식이 안전하다

### 완료 기준
- [ ] 에디터에서 임의 코드 진행을 만들어도 도수·기능·`ii-V-I` 그룹이 붙는다
- [ ] 같은 진행 재요청 시 캐시 히트(응답 시간 급감)
- [ ] `ambiguityScore` 가 응답에 포함된다 (BR-18의 입력이 된다)

### 프론트 연동점
응답을 `data/leadSheetTypes.ts` 의 `LeadSheetChordAnalysis` 모양으로 맞추면
`api/chordContext.ts::buildChordContext` 를 **한 줄도 안 고치고** 재사용할 수 있다.

## BR-18. `chordContext` **객체**가 RAG agent 로 전달되지 않아, 모호성 기반 쿼리 분해가 죽어 있다
`미해결` · HIGH · BE / RAG

### 설계상 이렇게 돌아야 한다 (HarmRAG)
```
사용자 질문
   ↓
룰엔진 태깅 (코드 기능·패턴·모호성 점수)
   ↓
ambiguity ≥ 0.5 ?
   ├─ 아니오 → 단일 해석으로 검색
   └─ 예     → 질문을 4~8개 sub-query 로 분해
                 ↓
          벡터 검색(ChromaDB/pgvector)
                 ↓
             RRF 로 결과 융합
                 ↓
        context assembly → Claude
```

### 그런데 실제로는
RAG agent 의 `decompose_query` 는 `chord_context.function`, `secondary_dominant`, `patterns_detected` 같은
**구조화된 필드**를 읽어서 sub-query 를 만든다.

**그런데 프론트는 `chord_context_text`(사람이 읽는 긴 문자열) 하나만 보낸다.** 객체는 안 보낸다.
→ agent 가 읽을 필드가 없다 → **코드 특화 쿼리 분해가 사실상 동작하지 않는다.**
(근거: `docs/RULE_BASED_BACKEND_INTEGRATION.md` §2.2)

### 왜 문제인가 (쉽게)
"모호한 코드는 여러 해석을 함께 보여 준다"가 Jazzify의 핵심 차별점인데,
**그 분기를 타는 조건 자체가 만들어지지 않는다.** 사실상 단일 쿼리 검색에 가깝게 동작한다.

### 좋은 소식
프론트는 **이미 객체를 보낼 준비가 돼 있다.**
```ts
// src/api/chat.ts  — 이미 존재하는 필드
export interface ChatStreamRequest {
  message: string;
  chordContext?: Record<string, unknown>;   // ★ 구조화 객체 (현재 미사용)
  chordContextText?: string;                // 현재 이것만 보냄
  useRag?: boolean;
  ...
}
```

### 백엔드가 할 일
1. `/v1/chat/*/stream` 요청 body 의 **`chordContext`(객체)를 받아서** RAG agent 에 그대로 넘긴다.
2. `ambiguityScore ≥ 0.5` 게이팅과 **sub-query 분해(4~8개)** 를 실제로 켠다.
3. 분해된 쿼리를 `RAG_DEBUG.queries` 에 실어 보낸다 (디버그 패널이 검증에 쓴다).

#### 요청 예시 `제안`
```jsonc
POST /v1/chat/chord-project/stream
{
  "message": "여기 F-7은 왜 나온 거야?",
  "useRag": true,
  "chordContextText": "Bar 21: F-7 | degree=iv | ...",   // 지금도 보냄 (유지)
  "chordContext": {                                       // ★ 새로 수용
    "song": "Autumn Leaves",
    "focus": { "bar": 21, "symbol": "F-7" },
    "function": "SD",
    "secondaryDominant": null,
    "patternsDetected": ["modal_interchange"],
    "ambiguityScore": 0.89,
    "interpretations": ["subdominant minor", "color chord"]
  }
}
```

### 완료 기준
- [ ] 모호한 코드(예: 장조 진행 속 차용 `iv` 계열)로 질문하면
      RAG 디버그 패널(F2.11)에 **sub-query 가 2개 이상** 표시된다
- [ ] 답변이 **복수 해석을 근거와 함께** 제시한다
- [ ] `ambiguityScore < 0.5` 인 평범한 코드는 단일 쿼리로 동작한다(불필요한 비용 증가 없음)

### 문서 정합성 (중요)
발표·사업계획서의 HarmRAG 도식은 이 흐름이 **런타임에 돈다**고 그려져 있다.
BR-17·18을 구현하면 도식이 사실이 되고, 구현하지 않는다면 **문서 표현을 "사전 분석 결과 활용"으로 고쳐야 한다.**

## BR-2. 공유 링크용 토큰 엔드포인트가 없다
`미해결` · MEDIUM · BE

**지금** — 공유(코드차트 F3.16 · 악보 F4.11)는 **차트 전체를 URL 해시에 통째로 인코딩**하는 프론트 전용 v1이다.

1. 차트가 크면 URL이 폭증한다 (특히 악보는 음표가 많다 → 일부 메신저가 링크를 자른다)
2. 공유 후 원본을 고쳐도 링크엔 반영 안 된다 (스냅샷)
3. 조회수·만료·폐기를 할 수 없다
4. 악보는 **보기 전용** — 받은 사람이 "내 것으로 복제"할 백엔드 경로가 없다

**백엔드가 할 일 `제안`**
```

DELETE /v1/chord-projects/{publicId}/share   → 폐기
```
악보 프로젝트도 동일 패턴 + **악보 import(복제) 경로** 추가.

**완료 기준** — 짧은 링크가 발급되고, 비로그인 브라우저에서 열리며, 폐기하면 404가 된다.

**프론트 연동점** — `lib/share/chartShare.ts` 의 `buildShareUrl` / `buildNoteShareUrl` 이 링크 소스만 토큰으로 바꾸면 된다(뷰어·복제 흐름 재사용).

## BR-21. RAG 디버그 블록의 **필드 계약**을 확정해 달라
`요청` · LOW · BE / RAG

> BR-13은 "마커를 **넣을지 말지**", 이 항목은 "넣는다면 **안에 무엇이 들어가는지**" — 서로 다른 문제다.

프론트(`api/harmorag.ts`)는 아래 필드를 전부 **optional** 로 선언해 뒀다. 백엔드가 실제로 채워 주는지 확정되지 않았기 때문이다.

| 필드 | 의미 |
|---|---|
| `status` | `'connected'` / `'offline'` — 이번 턴에 RAG가 실제로 돌았는지 |
| `top_k`, `total_retrieved` | 검색 파라미터·결과 수 |
| `fusion`, `rrf_k` | 융합 방식(`rrf`/`score`)과 파라미터 |
| `rrf_score` (청크별) | 정렬 기준 점수 |
| `matched_queries[]` (청크별) | 그 청크를 회수한 **모든** sub-query |

**왜 필요한가** — 이 필드들이 비면 RAG 디버그 패널(F2.11)의 쿼리 분해·RRF 시각화가 반쯤 빈다.
또 유튜브 인용 딥링크(F2.8)는 `source_type='youtube'` + `video_id` + `start_sec` 이 채워져야 동작한다.

**할 일** — 위 필드를 **항상 채워서** 내려보내고 스키마를 API 문서에 고정. RAG 미실행 턴은 `status: "offline"` 을 명시.

## BR-22. 오류 응답에서 내부 예외 문자열(`detail`)을 빼 달라
`요청` · LOW · BE / 보안

백엔드 오류 응답에 `detail`(내부 예외 문자열)이 들어온다.
프론트는 이걸 화면에 안 띄우고 dev 콘솔에만 찍는다 — **즉 지금은 프론트가 가려 주고 있을 뿐**이다.

**왜 문제인가** — API를 직접 호출하면 스택·SQL·내부 경로가 그대로 보인다. 공격자에게 지도를 주는 셈이다.

**할 일** — 운영 환경 응답에서 `detail` 을 **제거**하고 `code` / `message` 만 반환한다.
디버깅은 서버 로그 + 상관관계 ID(`traceId`)로 대체한다.
