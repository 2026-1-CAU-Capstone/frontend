# 2026-08-08 · 릭·솔로 읽기 권한 분리 + 내 릭 조회 3건

🏷 **범주(태그):** 콘텐츠·라이브러리·스토리지

큐레이션 릭·솔로 DB(391건)가 **로그인만 하면 누구나 전부 읽을 수 있다.** 쓰기는 role 로 막혀 있는데 읽기에는 role 규칙이 없다. 실서비스 오픈 전에 닫아야 한다.

범례: ✅ 완료 · 🟡 진행중 · ⬜ 미시작

- ⬜ 3. 릭 추천용 공개 목록 (1번의 선결 조건)

## 1. 릭·솔로 전역 목록 조회를 ADMIN·MANAGE 로 제한  ⬜ 미시작

### 기능 요약
`GET /v1/licks`·`GET /v1/solos`(및 단건·연주자·작곡가 목록)를 관리자 등급만 읽을 수 있게 한다.

### 상황 설명
`SecurityConfig` 에 쓰기는 등급 규칙이 있는데 읽기는 없다.

```java
.requestMatchers(HttpMethod.POST,   "/v1/licks/**").hasAnyRole("ADMIN", "MANAGE")
.requestMatchers(HttpMethod.PUT,    "/v1/licks/**").hasAnyRole("ADMIN", "MANAGE")
.requestMatchers(HttpMethod.DELETE, "/v1/licks/**").hasAnyRole("ADMIN", "MANAGE")
// GET 규칙이 없어 아래로 떨어진다
.anyRequest().authenticated()
```

그래서 **로그인한 아무나** 아래를 그대로 받는다(실측):

```
GET /v1/licks?size=500   → 153건, sheetData 전체 포함
GET /v1/solos?size=500   → 238건, sheetData 전체 포함
```

이 391건은 사내에서 OMR·채보로 구축한 자산이고, 그중에는 작업 중(`omrStatus=PROCESSING` 3건)·실패(`FAILED` 12건)·후보(`performer='candidate'` 128건)처럼 **외부에 보여선 안 되는 상태**가 섞여 있다. 지금은 계정이 관리자와 유령 계정뿐이라 부를 사람이 없지만, 오픈하면 첫 가입자부터 접근 가능하다.

프론트에서 화면을 지워도 닫히지 않는다 — 토큰만 있으면 API 를 직접 부를 수 있다.

### 기능 상세
- **사용자**: 관리자(내부 스튜디오)
- **권한**: `ADMIN` 또는 `MANAGE`. 그 외 로그인 사용자는 403
- **시나리오**: 일반 사용자가 토큰으로 `GET /v1/licks` 를 호출 → 403. 관리자는 지금과 동일하게 전체를 받는다
- **동작 조건**:
  - `GET /v1/licks/**`, `GET /v1/solos/**` 를 `hasAnyRole("ADMIN","MANAGE")` 로 (쓰기와 같은 규칙)
  - 연주자·작곡가 목록(`/v1/licks/performers`, `/composers`, 솔로 동일)도 함께 — 목록만으로도 DB 구성이 드러난다
  - ⚠️ **3번(공개 목록)이 먼저 있어야 한다.** 지금 AI 채팅의 릭 추천이 이 엔드포인트를 읽는다. 3번 없이 이것만 적용하면 추천 기능이 401/403 을 받고 **프론트가 조용히 낡은 번들 스냅샷으로 폴백한다**(기능이 죽지 않고 퇴화해서 눈치채기 어렵다)
  - 솔로는 3번이 필요 없다 — 실서비스 코드에서 전역 솔로를 읽는 곳이 0곳이다(사용자용 악보는 `sheet-projects` 로 간다). 솔로는 바로 제한 가능
- **검증 조건**:
  - 일반 사용자 토큰으로 `GET /v1/licks?size=1` → 403
  - 관리자 토큰으로 같은 호출 → 200, `totalElements` 153
  - 일반 사용자 토큰으로 `GET /v1/licks/{publicId}` → 403
  - 일반 사용자 토큰으로 `GET /v1/licks/performers` → 403
  - 솔로 4종 동일
- **기대 결과 및 완료 기준**:
  - [ ] `GET /v1/solos/**` 가 `ADMIN`·`MANAGE` 전용
  - [ ] `GET /v1/licks/**`(전역) 가 `ADMIN`·`MANAGE` 전용 — 단 3번 배포 이후
  - [ ] 연주자·작곡가 목록도 동일 규칙
  - [ ] 일반 사용자 토큰으로 큐레이션 데이터를 한 건도 받을 수 없다

## 2. 내 릭 조회 — 토큰 사용자가 만든 릭만  ⬜ 미시작

### 기능 요약
사용자가 자기 릭만 받아오는 엔드포인트. **코드 프로젝트가 이미 하는 방식과 같게.**

### 상황 설명
코드 차트·악보 차트는 서버가 소유자로 좁힌다.

```java
// ChordProjectRepository
Page<ChordProject> findAllByUserAndDeletedAtIsNull(User user, Pageable pageable);
Optional<ChordProject> findByPublicIdAndUserAndDeletedAtIsNull(UUID publicId, User user);
```

프론트는 `GET /v1/chord-projects` 만 부르고 소유자 조건을 보내지 않는다 — 서버가 토큰으로 좁히므로 남의 것은 응답에 담기지 않는다. 단건도 `AndUser` 라서 남의 `publicId` 를 알아도 못 가져온다. **이게 올바른 형태다.**

릭 리포지토리에는 소유자 기준 쿼리가 없다.

```java
// LickRepository — userId 로 찾는 메서드가 없다
Optional<Lick> findByPublicId(UUID publicId);
Page<Lick> findByComposerIgnoreCase(String composer, Pageable pageable);
Page<Lick> findByPerformerIgnoreCase(String performer, Pageable pageable);
```

그래서 프론트가 "내 릭"을 이렇게 만든다:

```ts
const all = await loadLicks();                     // 전체 153건을 받아서
mine = all.filter(l => l.source === 'user'
                    && l.userId === me.publicId);  // 클라이언트에서 걸러낸다
```

**내 릭 3건을 보려고 전체 153건을 내려받는다.** 화면에는 내 것만 보이지만 브라우저는 전부 받았고, 개발자 도구에 그대로 남는다. 1번을 적용하면 이 화면이 아예 깨진다 — 그래서 1번과 짝으로 필요하다.

### 기능 상세
- **사용자**: 로그인 사용자
- **권한**: 로그인 필요 · **본인 것만**
- **시나리오**: 사용자가 "내 릭" 화면 진입 → 자기가 만든 릭만 페이지로 받는다
- **동작 조건**:
  - 경로는 백엔드 판단에 맡긴다. 프론트가 호출할 계약만 `제안`:
    ```
    GET /v1/licks/mine?page=0&size=20
    → { data: { content: [...], totalElements, totalPages, ... } }   // 기존 페이지 봉투와 동일
    ```
  - 응답 요소는 기존 `LickResponse` 와 같은 모양이면 프론트 타입 재생성만으로 붙는다
  - 소유자 판정은 토큰에서 — 쿼리 파라미터로 `userId` 를 받지 않는다(남의 것을 요청할 수 있게 된다)
  - `Lick.userId` 는 지금 FK 가 아니라 `@Nullable UUID` 다. 소유자 판정을 이 컬럼으로 할지 `User` 연관으로 바꿀지는 백엔드 판단
- **검증 조건**:
  - 사용자 A 토큰으로 호출 → A 가 만든 것만. B 의 릭이 한 건도 없다
  - 릭을 만든 적 없는 사용자 → `content: []`, `totalElements: 0` (404 아님)
  - 관리자로 호출 → 관리자가 만든 것만(전체가 아니라)
- **기대 결과 및 완료 기준**:
  - [ ] 본인 릭만 페이지로 반환
  - [ ] 응답에 남의 릭이 섞이지 않는다
  - [ ] 프론트가 클라이언트 필터를 지울 수 있다

## 3. 릭 추천용 공개 목록  ⬜ 미시작  (1번의 선결 조건)

### 기능 요약
AI 채팅의 릭 추천이 읽을, **공개해도 되는 릭만** 담은 목록.

### 상황 설명
지금 `GET /v1/licks` 하나에 용도 셋이 뭉쳐 있다.

| 용도 | 누가 | 무엇을 |
|---|---|---|
| 내 릭 | 본인 | 자기가 만든 것 |
| **추천** | 로그인 사용자 | 공개 가능한 것 |
| 관리 | ADMIN·MANAGE | 전부(작업 중·실패·후보 포함) |

뭉쳐 있으니 **막으면 추천이 죽고, 열어두면 DB 가 샌다.** 갈라야 풀린다.

문제는 "공개 가능한 것"을 판정할 근거가 데이터에 없다는 점이다 — 현재 릭 153건이 전부 `source: 'unknown'` 이고 공개 여부·승인 상태 필드가 없다.

**제품 결정(2026-08-08):** 기존 153건은 **전부 비공개**다. 사내에서 구축한 DB 라 사용자에게 보여선 안 된다.

그 결과 이 엔드포인트는 **당분간 빈 목록을 반환**한다. 의도된 상태다 — 추천 기능은 공개할 릭을 골라 표시할 때까지 잠든다. 나중에 커뮤니티를 열면 "승인된 사용자 릭"이 이 목록에 들어온다.

### 기능 상세
- **사용자**: 로그인 사용자
- **권한**: 로그인 필요(등급 무관)
- **시나리오**: 채팅에서 릭 추천 요청 → 공개 릭 중에서 고른다. 공개 릭이 없으면 빈 목록(오류 아님)
- **동작 조건**:
  - `Lick` 에 공개 여부 필드 추가. 이름·타입은 백엔드 판단(`isPublic boolean` 또는 `visibility` enum). **기존 153건 기본값은 비공개**
  - 프론트가 호출할 계약만 `제안`:
    ```
    GET /v1/licks/public?page=0&size=100
    → { data: { content: [...], totalElements, ... } }
    ```
  - 응답 필드는 **축약**을 제안한다 — 추천에 필요한 것만. 내부 운영 필드(`omrStatus`·`omrProgress`·`omrFailureReason`·`userId`·`source`)는 빼는 게 좋다. 필요 필드: `publicId` · `title` · `performer` · `composer` · `instrument` · `style` · `tempo` · `key` · `timeSignature` · `chords` · `targetChord` · `sheetData` + 유사도 특징(`intervals`·`parsons`·`pitches`·`durationClasses` 등 — 프론트가 코드 진행 매칭에 쓴다)
  - 공개 여부를 바꾸는 수단(스튜디오에서 릭을 공개로 전환)은 이 문서 범위 밖 — 필요해지면 별도 요구사항으로 올린다
- **검증 조건**:
  - 일반 사용자 토큰으로 호출 → 200, 현재는 `totalElements: 0`
  - 한 건을 공개로 바꾸고 호출 → 그 한 건만
  - 응답에 `omrStatus`·`userId` 등 내부 필드가 없다
  - `performer='candidate'`(후보 128건)·`omrStatus=FAILED`(12건)는 공개로 바꿔도 노출되지 않는지 확인(이중 안전장치를 둘지는 백엔드 판단)
- **기대 결과 및 완료 기준**:
  - [ ] `Lick` 에 공개 여부 필드, 기존 153건 전부 비공개
  - [ ] 공개 목록 엔드포인트가 로그인 사용자에게 열려 있다
  - [ ] 응답에 내부 운영 필드가 없다
  - [ ] 이게 배포된 뒤에 1번(전역 목록 제한)을 적용한다
