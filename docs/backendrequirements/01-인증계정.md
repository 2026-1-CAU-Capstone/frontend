# 2026-07-15 · 인증·계정 요구사항 2건

🏷 **범주(태그):** 인증·계정
로그인(소셜/이메일)·회원가입·등급(role)·세션. 프론트는 이미 UI/세션 소비 준비 완료, 백엔드 발급만 필요.

## 진행 현황
범례: ✅ 완료 · 🟡 진행중 · ⬜ 미시작

## 1. 사용자 등급(role) 반환  ⬜ 미시작  (← BR-6)

### 기능 요약
`GET /v1/auth/me`(및 로그인 응답)에 사용자 등급 `role` 필드를 추가한다.

### 상황 설명
사이드바 Admin 메뉴(Chord/Note/Lick/Solo/Editor/YouTube/OMR 관리)는 관리자에게만 보여야 한다. 그런데 `/v1/auth/me`·로그인 응답에 등급 필드가 없어, 프론트가 "아이디가 `admin`인지"를 문자열로 임시 판별 중이다(보안 아님).

### 기능 상세
- **사용자**: 일반 사용자, 관리자
- **권한**: 로그인 필요
- **시나리오**: 로그인 → `/auth/me` 조회 → `role` 확인 → `ADMIN`이면 관리 메뉴 노출
- **동작 조건**
  - 응답에 `role` 포함. `제안`:
    ```jsonc
    // GET /v1/auth/me
    { "id": 12, "username": "benzity", "email": "...", "role": "ADMIN" }  // "ADMIN" | "USER"
    ```
  - 가능하면 **로그인 응답에도** `role` 포함(첫 화면부터 반영).
  - 관리자 등급 부여/회수 수단 필요.
  - ⚠️ 프론트의 `role`은 화면 숨김 용도일 뿐 — **admin 전용 API는 서버에서 반드시 재검사**.
- **검증 조건**: 일반 사용자가 admin API를 직접 호출하면 **403**.
- **기대 결과 및 완료 기준**
  - [ ] `/v1/auth/me`가 `role` 반환
  - [ ] admin API 무권한 호출 시 403
  - [ ] 프론트에서 아이디 문자열 판별(`username === 'admin'`) 제거 가능 (`api/auth.ts::isAdminUser`가 자동 전환)

## 2. 소셜 로그인(OAuth)  ⬜ 미시작  (← BR-16)

### 기능 요약
Google 등 소셜 로그인(OAuth) 백엔드를 구현하고 기존 세션 발급에 합류시킨다.

### 상황 설명
로그인 화면의 Google 버튼은 UI만 있고, 누르면 "곧 지원됩니다" 토스트가 뜬다. 백엔드 인가 플로우가 없다.

### 기능 상세
- **사용자**: 비로그인 방문자
- **권한**: 불필요(로그인 과정)
- **시나리오**: Google 버튼 → 인가 코드 플로우(redirect → callback) → 세션 발급 → 로그인 완료. 신규 사용자면 자동 회원가입.
- **동작 조건**
  - OAuth 인가 코드 플로우 구현 후 **기존 JWT/RTR 세션 발급 로직에 합류**.
  - ⚠️ **신규 세션 체계를 따로 만들지 말 것** (기존 로그인과 동일 세션).
- **검증 조건**: Google 로그인으로 발급된 세션이 이메일 로그인과 동일하게 보호 라우트에 접근.
- **기대 결과 및 완료 기준**
  - [ ] Google 로그인 → 일반 로그인과 동일한 세션 획득
  - [ ] 신규 계정 자동 생성
