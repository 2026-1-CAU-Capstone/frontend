## 1. 솔로 OMR — 사용자 입력 title/performer 우선  ✅ 완료  (← BR-30)

> **2026-07-29 검증**: `SoloService.firstText()` 가 `사용자 입력 > OMR 추출 > 기본값` 우선순위를 구현(`SoloService.java:304-305, 352-359`). 실측 — 2026-07-28 OMR 생성 15건이 모두 입력값 그대로 저장돼 있고, 문서의 `performer=Unknown` / `title=Dbmmai7` 증상은 재현되지 않는다. 도입 커밋 `7ebfb28`.

### 기능 요약
`POST /v1/solos/omr` 저장 시, 요청 `metadata`(`SoloOmrRequest`)에 담긴 `title`·`performer`(및 기타 메타)를 **인식된 MusicXML 추출값보다 우선** 적용한다.

### 상황 설명
사용자가 업로드 모달에서 제목·연주자를 직접 입력해도(예: 제목 `test`, 연주자 `test`), 저장된 솔로는 **연주자 `Unknown`, 제목 `Dbmmai7`** 로 기록된다. 즉 프론트가 보낸 `metadata.title`/`performer` 가 무시되고, OMR이 인식한 MusicXML의 `work-title`/파트정보 등에서 뽑은 값으로만 저장된다.

- **실측(2026-07-19, admin)**: 당일 `POST /v1/solos/omr` 업로드 6건이 모두 `performer=Unknown, title=Dbmmai7` 로 저장됨. 입력 메타데이터와 무관하게 동일 결과.
- 스펙 대조: `SoloOmrRequest` 스키마에는 `title`·`performer`·`composer`·`album`·`instrument`·`style`·`tempo`·`key`·`timeSignature`·`rhythmFeel` 필드가 **정의돼 있고**, 프론트는 이를 `metadata` 파트(JSON)로 실제 전송한다. 그럼에도 저장 결과에 반영되지 않는다.
- 영향: 사용자가 만든 솔로가 의도한 이름으로 저장되지 않아 **연주자 목록(디렉터리)에서 찾을 수 없고**, 전부 `Unknown` 에 뭉쳐 축적된다. OMR 제목 추출 품질이 낮아(예: `Dbmmai7` 같은 코드기호/문자열) 방치 시 라이브러리가 오염된다.

### 기능 상세
- **사용자**: 로그인 사용자(솔로 OMR 업로드)
- **권한**: 로그인 필요, 본인 콘텐츠
- **시나리오**: 업로드 모달에서 제목·연주자 입력 → 이미지 업로드 → `POST /v1/solos/omr` → 저장된 솔로의 title/performer 가 **입력값과 일치**
- **동작 조건**
  1. `metadata.title` 이 비어있지 않으면(공백 트림 후 길이>0) 저장 title 은 그 값을 사용한다. 비어 있으면 OMR/MusicXML 추출값으로 폴백.
  2. `metadata.performer` 도 동일 규칙(입력값 우선, 없으면 추출값, 그것도 없으면 `Unknown`).
  3. 나머지 메타(`composer`·`album`·`instrument`·`style`·`tempo`·`key`·`timeSignature`·`rhythmFeel`)도 **입력값 우선, 없으면 추출값** 규칙을 동일 적용.
  4. 우선순위 요약(제안): `사용자 입력값 > OMR/MusicXML 추출값 > 기본값(Unknown 등)`.
  - 프론트가 보내는 요청 형태(현행, 참고): `multipart/form-data` 의 `file`(binary) + `metadata`(JSON, `application/json`). `제안`:
    ```jsonc
    // metadata 파트 (SoloOmrRequest)
    {
      "title": "test",        // 비어있지 않으면 이 값으로 저장돼야 함
      "performer": "test",    // 비어있지 않으면 이 값으로 저장돼야 함
      "source": "user"
      // album/instrument/style/tempo/key/timeSignature/rhythmFeel 은 생략 가능
    }
    ```
- **검증 조건**
  1. `title="test"`, `performer="test"` 로 이미지 1건 업로드 → 저장된 솔로 조회 시 `performer=="test"`, `title=="test"`.
  2. `metadata` 를 생략하거나 두 필드를 비워서 업로드 → 기존처럼 추출값(없으면 `Unknown`)으로 저장(회귀 없음).
  3. `GET /v1/solos?performer=test` 또는 연주자 facet 집계에 `test` 가 노출된다.
- **기대 결과 및 완료 기준**:
  - [x] 입력한 title/performer 가 저장 결과에 그대로 반영된다.
  - [x] 메타 미입력 시 기존 추출/기본값 동작이 유지된다(회귀 없음) — `firstText()` 폴백 체인으로 보장.
  - [x] 연주자 목록/검색에서 사용자가 지정한 이름으로 찾을 수 있다.

## 2. `GET /v1/solos/{publicId}/omr-status` 500 복구·구현  ✅ 완료  (← BR-31)

> **2026-07-29 검증**: 엔드포인트가 OpenAPI 스펙에 등록되고 구현됨(`SoloController.java:95-99`). 문서에 500 사례로 적힌 `publicId` `43b01410-e2c0-41ac-a31c-f8a265cded84` 를 실호출하니 **200 `COMPLETED`**. 존재하지 않는 id 는 404(500 아님). sheet/chord-project 와 동일한 status/progress/failureReason 규격.

### 기능 요약
솔로 OMR 진행 상태 폴링 엔드포인트 `GET /v1/solos/{publicId}/omr-status` 가 `sheet-projects`/`chord-projects` 와 동일한 규격으로 정상 응답하도록 구현/복구한다.

### 상황 설명
프론트는 비동기 OMR 진행률(대기/처리중/완료/실패)을 실시간 상태창에 표시하려고 이 엔드포인트를 폴링한다. 그러나 현재 **HTTP 500 `GLOBAL_001`** 을 반환한다.

- **실측(2026-07-19, admin)**: 실제 솔로 `publicId`(예: `43b01410-e2c0-41ac-a31c-f8a265cded84`)로 호출 시 `500 {"code":"GLOBAL_001","message":"서버 내부 오류가 발생했습니다."}`.
- 스펙 대조: OpenAPI(`/v3/api-docs`)에 `GET /v1/sheet-projects/{publicId}/omr-status`·`GET /v1/chord-projects/{publicId}/omr-status` 는 등록돼 있으나, **`solos` 용은 문서에 없다**(라우트는 존재하는지 500만 반환).
- 영향: 프론트 상태 패널이 실제 진행률(%)을 채우지 못한다. (현재는 생성 응답 promise로 완료/실패만 표시하는 폴백으로 동작 중.)

### 기능 상세
- **사용자**: 로그인 사용자(솔로 OMR 업로드 후 진행 확인)
- **권한**: 로그인 필요, 본인 콘텐츠
- **시나리오**: 업로드 직후 프론트가 5초 간격으로 상태 폴링 → 상태창에 대기/처리중(%)/완료/실패 실시간 표시
- **동작 조건**
  1. 유효한 솔로 `publicId` 로 호출 시 `200` + 아래 형태(제안)를 반환. `chord/sheet-project` 규약과 동일 필드로 통일:
     ```jsonc
     // 200 응답 (ApiResponse 봉투 안 data)
     {
       "publicId": "….",
       "status": "PENDING | PROCESSING | COMPLETED | FAILED",
       "progress": 0,               // 0..100 (정수), 미측정이면 0
       "failureReason": null         // FAILED 일 때 사유 문자열, 아니면 null
     }
     ```
  2. 존재하지 않는 `publicId` → `404`(500 아님).
  3. OMR 이력이 없는(동기 처리로 이미 완료된) 솔로 → `500` 대신 `COMPLETED` 로 응답하거나 `404` 로 명확히 구분.
  4. OpenAPI(`/v3/api-docs`)에 엔드포인트·응답 스키마를 등록(프론트 타입 생성용).
- **검증 조건**
  1. 방금 업로드해 처리 중인 솔로 → 폴링하면 `PROCESSING`(가능하면 progress 증가) → 최종 `COMPLETED`.
  2. 완료된 기존 솔로 → 500 없이 `COMPLETED`(또는 규정된 응답).
  3. 잘못된 id → `404`.
- **기대 결과 및 완료 기준**:
  - [x] 유효 id 호출이 500 없이 정의된 상태 JSON을 반환한다.
  - [x] `sheet/chord-project` 와 동일한 status/progress/failureReason 규격을 따른다.
  - [x] OpenAPI 문서에 노출되어 프론트 타입 자동생성에 포함된다.
