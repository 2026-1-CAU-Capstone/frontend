## 1. Google 로그인 — ID 토큰 검증 후 자체 토큰 발급  ⬜ 미시작

### 기능 요약
Google 계정으로 로그인해 기존과 **같은 형태의 access token + refresh 쿠키**를 받는다.

### 상황 설명
지금 로그인 수단은 아이디·비밀번호뿐이다. 프론트의 Google 버튼은 스텁이다.

```ts
const handleSocial = (name: string) => {
  setError(`${name} 로그인은 곧 지원됩니다.`);
};
```

`tb_user` 에는 **email 컬럼이 없다.**

```java
@Table(name = "tb_user")
  private String name;                     // 표시 이름
  private String username;   // unique     // 로그인 아이디
  private String password;   // nullable=false
  private UserRole role = UserRole.MEMBER; // ADMIN · MANAGE · MEMBER
```

`application-prod.yml` 에 OAuth2 설정이 주석으로 준비돼 있다(google · kakao).

**왜 지금 하는가**: 실서비스 오픈 전에 계정 체계를 확정해야 한다. 비밀번호를 없애면 재설정·유출·재사용 문제가 통째로 사라진다. 지금은 관리자 계정과 유령 계정뿐이라 **기존 계정을 Google 로 이관할 필요가 없다** — 이관 없이 새로 시작할 수 있는 마지막 시점이다.

### 기능 상세
- **사용자**: 비로그인 방문자(신규·기존 무관)
- **권한**: 불필요
- **시나리오**:
  1. 로그인 화면에서 "Google로 계속하기"
  2. Google 계정 선택·동의
  3. 백엔드가 신원을 확인하고 계정을 찾거나 만든다
  4. 기존 로그인과 **같은 응답**을 받아 프론트는 분기 없이 그대로 진행
- **동작 조건**:

  **인증 방식** — 두 가지가 있다. 프론트는 `제안`으로 **(A) ID 토큰 방식**을 선호하고, 최종 선택은 백엔드에 맡긴다.

  **(A) ID 토큰 방식 (제안)** — SPA 가 Google 에서 ID 토큰을 받아 백엔드에 넘긴다.
  ```
  POST /v1/auth/google
  { "idToken": "<Google ID token>" }

  → 200 { data: { accessToken, publicId, username, role, name } }
    + Set-Cookie: refreshToken=…  (기존과 동일: HttpOnly · Secure · SameSite=None · path=/api)
  ```
  - 백엔드가 Google 공개키로 ID 토큰 서명·`aud`·`exp` 를 검증한다
  - 기존 `POST /v1/auth/login` 과 **응답 모양이 같아야** 프론트가 한 경로로 처리한다

  이 방식을 선호하는 이유: 프론트가 HashRouter SPA 라 리다이렉트 방식(B)은 `#/…` 경로와 토큰 전달이 꼬인다. 토큰을 URL 로 넘기면 브라우저 히스토리·리퍼러에 남는다. 그리고 지금의 access token + refresh 쿠키 계약을 **그대로 유지**할 수 있어 프론트 변경이 로그인 버튼 하나로 끝난다.

  **(B) Spring Security OAuth2 리다이렉트** — `/oauth2/authorization/google` → Google → `/login/oauth2/code/google`. `application-prod.yml` 주석이 이 방식을 향해 있다. 백엔드가 이쪽을 택하면 **성공 후 SPA 로 돌아올 방법**(어느 URL 로, 토큰을 어떻게 전달)을 정해 알려주면 프론트가 맞춘다.

  **계정 매칭**
  - `email` 을 계정의 유일 키로 둘 것을 제안한다. Google `sub`(고유 ID)도 함께 저장하면 이메일 변경에도 같은 계정을 유지할 수 있다
  - 같은 이메일로 이미 계정이 있으면 **새로 만들지 않고 연결**한다
  - `username` 은 지금 `unique` + `not null` 이다. Google 사용자에게 무엇을 넣을지 정해야 한다(이메일 앞부분 + 충돌 시 접미사 / 또는 nullable 로 완화). 프론트는 표시에 `name` 을 우선 쓰고 없으면 `username` 을 쓴다
  - `password` 는 지금 `not null` 이다. Google 사용자는 비밀번호가 없으므로 **nullable 로 완화**가 필요하다(2번 항목 이후 7단계에서 컬럼 자체를 드롭할 예정)

  **role 부여**
  - 신규 계정은 `MEMBER`
  - `ADMIN` 은 **환경변수 allowlist** 로 부여할 것을 제안한다(예: `ADMIN_EMAILS`). 목록에 있는 이메일로 로그인하면 `ADMIN`
  - ⛔ 코드에 이메일을 하드코딩하지 않는다 — repo 가 유출되면 공격 대상이 노출된다
  - ⛔ "특정 Google 계정이면 admin" 을 **프론트에서 판정하지 않는다.** 프론트는 서버가 준 `role` 만 신뢰한다

  **CORS·오리진**
  - 스튜디오가 별도 도메인으로 배포된다(`jazzifystudio.netlify.app`). `CORS_ALLOWED_ORIGINS` 에 추가 필요
  - Google Cloud Console 의 승인된 자바스크립트 원본·리디렉션 URI 에 실서비스·스튜디오·로컬(`http://localhost:5173`·`:5174`) 을 등록해야 한다. 클라이언트 ID 는 프론트 번들에 박히므로(공개돼도 되는 값) `VITE_GOOGLE_CLIENT_ID` 로 받는다. **클라이언트 시크릿은 백엔드에만** 둔다

- **검증 조건**:
  - 새 Google 계정으로 로그인 → 계정이 생기고 `role: "MEMBER"`
  - 같은 계정으로 다시 로그인 → 계정이 새로 생기지 않는다(총 사용자 수 불변)
  - `ADMIN_EMAILS` 에 넣은 계정으로 로그인 → `role: "ADMIN"`, 스튜디오 진입 가능
  - 응답 모양이 `POST /v1/auth/login` 과 동일 → 프론트가 분기 없이 처리
  - refresh 쿠키가 내려오고 `POST /v1/auth/refresh` 가 그 쿠키로 갱신된다
  - 위조·만료된 ID 토큰 → 401 (계정이 생기지 않는다)
- **기대 결과 및 완료 기준**:
  - [ ] Google 로그인으로 기존과 같은 토큰·쿠키를 받는다
  - [ ] `tb_user` 에 email(+ Google 고유 ID) 저장, 같은 이메일은 계정 하나
  - [ ] `password` nullable 완화
  - [ ] `ADMIN` 이 환경변수 allowlist 로 부여된다
  - [ ] 위조 토큰이 거부된다

## 2. login 응답에 `role` 포함  ⬜ 미시작  (← BR-6 남은 절반)

### 기능 요약
`POST /v1/auth/login` 응답에 `role` 을 넣는다.

### 상황 설명
BR-6("`/v1/auth/me` 에 role 부재")은 **절반 해결됐다.** 실측(2026-08-08):

```
GET /v1/auth/me   → { username: "admin", role: "ADMIN" }   ✅
POST /v1/auth/login → { accessToken, publicId, username }   ← role 없음
```

`/me` 는 role 을 주는데 login 응답에는 없다. 그래서 프론트가 로그인 직후 한 프레임 동안 **아이디 기반 폴백**에 의존한다.

```ts
export function isAdminUser(user: AuthUser | null): boolean {
  if (user.role) return user.role.toUpperCase().includes('ADMIN');
  return user.username === 'admin';   // ← role 도착 전 임시 판정
}
```

로그인 직후 `fetchMe()` 가 배경에서 role 을 채우지만, 그 사이에 스튜디오 화면으로 들어가면 폴백이 판정한다. **아이디 문자열로 권한을 정하는 코드는 남겨둘 이유가 없다** — login 응답에 role 이 오면 이 줄을 지울 수 있다.

Google 로그인(1번)에서는 `username` 이 이메일 기반으로 생성될 수 있어 이 폴백이 아예 성립하지 않는다. 그래서 1번과 함께 처리하는 것이 자연스럽다.

### 기능 상세
- **사용자**: 로그인하는 모든 사용자
- **권한**: 불필요(로그인 응답 자체)
- **시나리오**: 로그인 → 응답에서 바로 등급을 알 수 있다 → 추가 호출 없이 화면 결정
- **동작 조건**:
  - `POST /v1/auth/login` 응답의 `data` 에 `role` 추가. 값은 `/v1/auth/me` 와 같은 형식(`ADMIN`·`MANAGE`·`MEMBER`)
  - 기존 필드(`accessToken`·`publicId`·`username`)는 그대로 — 추가만
  - 가능하면 `name` 도 함께(표시 이름. 지금은 `/me` 로 한 번 더 받아야 한다)
  - 1번의 Google 로그인 응답도 같은 모양
- **검증 조건**:
  - 관리자로 로그인 → `role: "ADMIN"`
  - 일반 계정으로 로그인 → `role: "MEMBER"`
  - 프론트가 `username === 'admin'` 폴백을 지워도 스튜디오 진입이 정상
- **기대 결과 및 완료 기준**:
  - [ ] login 응답에 `role`
  - [ ] Google 로그인 응답도 동일
  - [ ] 프론트가 아이디 기반 폴백을 제거할 수 있다
