## 1. 사용자 프로필 확정 + 프로필 사진(구글 연동)  ⬜ 미시작  (← BR-24)

### 기능 요약
사용자 프로필(닉네임·프로필 사진 등) 스키마를 확정하고, 구글 로그인 사용자는 구글 계정 프로필 사진을 자동으로 초기 프사로 등록한다.

### 상황 설명
현재 `/v1/auth/me`는 id·username·email 수준만 내려주고, 프로필 사진 개념이 서버에 없다. 프론트는 프사 표시 UI를 붙이려 해도 받을 필드가 없다. 구글 로그인(BR-16)이 붙으면 구글 계정의 프사를 자동으로 가져와 넣는 UX를 원한다.

### 기능 상세
- **사용자**: 로그인 사용자
- **권한**: 본인 것
- **시나리오**: 구글 로그인 → 구글 계정 프사가 자동으로 프로필에 등록 → `/auth/me`로 프로필 수신 → 화면 표시, 이후 사용자가 수정 가능
- **동작 조건**
  - 프로필 필드 확정 및 `/auth/me` 확장. `제안`:
    ```jsonc
    // GET /v1/auth/me
    { "id": 12, "username": "benzity", "email": "...", "role": "USER",
      "nickname": "벤", "profileImageUrl": "https://..." }   // 둘 다 nullable

    // PATCH /v1/users/me
    { "nickname": "벤", "profileImageUrl": "https://..." }
    ```
  - 구글 OAuth(BR-16) 로그인 시 구글 프로필 이미지(picture)를 `profileImageUrl` 초기값으로 저장. 이메일 가입자는 null(프론트가 기본 아바타 표시).
  - 이미지 파일 직접 업로드(스토리지 경유)는 **미정** — 1차는 URL 필드만.
- **검증 조건**: 구글 로그인 계정의 `/auth/me`에 구글 프사 URL이 들어 있다. PATCH 후 재조회에 반영된다.
- **기대 결과 및 완료 기준**
  - [ ] `/auth/me`에 `nickname`·`profileImageUrl` 포함
  - [ ] 구글 로그인 시 구글 프사 자동 등록
  - [ ] 본인 프로필 수정 API 동작

## 2. 악보 프로젝트 생성 + 프로젝트 채팅 저장  ⬜ 미시작  (← BR-25)

### 기능 요약
악보 프로젝트(SheetProject) 생성 플로우를 확정하고, 프로젝트에 연결된 채팅이 서버에 저장·복원되게 한다.

### 상황 설명
코드차트 프로젝트는 생성→채팅→이력 복원이 돌지만, 악보 프로젝트는 "생성 + 그 프로젝트 문맥의 채팅 저장"이 완결 계약으로 확정된 항목이 없다(BR-20이 chord/sheet-project 채팅 상세 응답을 언급할 뿐). 악보 프로젝트 화면에서 나눈 채팅이 새로고침 후 사라지면 안 된다.

### 기능 상세
- **사용자**: 로그인 사용자
- **권한**: 본인 프로젝트·본인 채팅
- **시나리오**: 악보 업로드 → 악보 프로젝트 생성 → 프로젝트 화면에서 AI 채팅 → 새로고침/다른 기기 로그인 → 채팅 이력 그대로 복원
- **동작 조건**
  - 악보 프로젝트 생성·조회가 코드차트 프로젝트와 동일 패턴으로 동작.
  - 악보 프로젝트에 연결된 채팅 생성/스트림/상세. `제안`:
    ```jsonc
    POST /v1/chat/sheet-project/stream
    { "sheetProjectId": "<publicId>", "message": "...", "useRag": true }
    // 상세는 기존과 동일: GET /v1/chat/{publicId} → messages 항상 포함(BR-20 정합)
    ```
  - 채팅↔프로젝트 연결이 저장되어, 프로젝트 상세에서 그 채팅을 다시 찾을 수 있어야 한다.
- **검증 조건**: 생성→채팅→새로고침 후 이력 동일. 프로젝트 삭제 시 연결 채팅 처리 정책(보존/삭제)이 명시돼 있다(정책 자체는 **미정** — 정해달라).
- **기대 결과 및 완료 기준**
  - [ ] 악보 프로젝트 생성·조회 동작
  - [ ] 프로젝트 연결 채팅이 서버 저장·복원됨

## 3. 악보 메타데이터 OCR 추천 API  ⬜ 미시작  (← BR-26)  [백엔드+OMR]

### 기능 요약
업로드된 악보/코드차트 이미지에서 제목·Composer·Player·Time Signature(+조표가 보이면 Key 후보)를 경량 OCR/OMR로 파싱해 **추천값**으로 반환하는 API.

### 상황 설명
지금은 사용자가 메타데이터를 전부 손으로 입력한다. 원하는 플로우는: 업로드 직후 경량 모델이 메타데이터 추천값을 주고, 사용자가 모달에서 수정·확정한다(추천은 확정이 아님 — 최종 값은 항상 사용자가 정한다).

Key는 **사용자 입력이 기본**이다: 조표가 파싱되는 악보면 그걸로 추천값을 채우고, 조표가 없는 코드차트면 빈칸으로 시작한다. (코드 진행 기반 Key 예측 모델은 여기서 돌리지 않고 BR-28의 경고용으로만 쓴다 — 전체 OMR이 끝나야 가능하기 때문.)

### 기능 상세
- **사용자**: 로그인 사용자
- **권한**: 로그인
- **시나리오**: 악보(또는 코드차트) 업로드 → 메타데이터 추천 수신 → 확정 모달에 프리필 → 사용자가 수정·확정
- **동작 조건**
  - `제안`:
    ```jsonc
    POST /v1/sheet-metadata/suggest   // multipart: file
    → { "title": "Autumn Leaves", "composer": "J. Kosma", "player": null,
        "key": "Gm",              // 조표 파싱 가능할 때만, 아니면 null
        "timeSignature": "4/4",
        "confidence": { "title": 0.93, "key": 0.71 } }
    ```
    처리 시간이 길면 비동기 잡+폴링으로 변경 가능(형태는 백엔드 재량, 프론트에 알려만 달라).
  - 확정 메타데이터 스키마: 업로드 시간·업로더 id(서버 자동), `title`, `key`, `timeSignature`. `genre`는 **미정**(포함 여부 애매 — 논의 필요).
  - 입력이 악보 차트인지 코드 차트인지 구분하는 경량 classifier는 **미정** — 1차는 구분 없이 동일 처리하고, 병목이 확인되면 추가 검토.
- **검증 조건**: 대표 악보/코드차트 샘플에서 제목·박자 추천이 채워지고, 응답 지연이 업로드 UX를 해치지 않는 수준(수 초 내 또는 비동기 진행 표시).
- **기대 결과 및 완료 기준**
  - [ ] 업로드 직후 메타데이터 추천값 수신(악보·코드차트 공통)
  - [ ] 조표 있는 악보는 `key` 추천, 없으면 null
  - [ ] 추천값이 사용자 확정을 덮어쓰는 일 없음(추천은 프리필 전용)

## 4. 확정 메타데이터 → Main OMR 실행 계약  ⬜ 미시작  (← BR-27)  [백엔드+OMR]

### 기능 요약
사용자가 모달에서 확정한 메타데이터를 받아 Main OMR을 실행하되, OMR이 그 메타데이터를 절대 덮어쓰지 않고, 백엔드가 OMR 결과(코드)와 확정 메타를 병합해 반환한다.

### 상황 설명
메타 추천(BR-26) 뒤 사용자가 수정 기회를 가진다. 그 확정값이 Main OMR/룰엔진을 거치는 동안 바뀌면 안 된다. OMR + 룰엔진 분석(BR-7·BR-17)까지 끝나야 비로소 코드차트가 활성화되는 것이 목표 플로우다: 업로드(1) → 메타 추천(2, BR-26) → 사용자 확정(3) → **Main OMR + 병합(4, 본 항목)** → 코드차트 활성화(5).

### 기능 상세
- **사용자**: 로그인 사용자
- **권한**: 본인 프로젝트
- **시나리오**: 메타 확정 → Main OMR 잡 시작 → 폴링 → 완료 시 "확정 메타 + OMR 코드 + 룰엔진 분석"이 병합된 결과 수신 → 코드차트 활성화
- **동작 조건**
  - 프로젝트 생성/OMR 시작 시 확정 메타데이터를 받는다. `제안`:
    ```jsonc
    POST /v1/chord-projects           // (기존 생성 엔드포인트 확장이면 그걸로)
    { "file": "...", "confirmedMetadata": {
        "title": "...", "key": "Gm", "timeSignature": "4/4" } }
    ```
  - OMR·분석 파이프라인은 `confirmedMetadata`를 **읽기 전용**으로 취급(덮어쓰기 금지).
  - 완료 응답은 확정 메타 + OMR 코드 + 룰엔진 분석(BR-7로 자동 실행)이 병합된 형태 — 프론트가 화면 활성화에 한 번의 조회로 충분해야 한다.
- **검증 조건**: 사용자가 추천값에서 바꾼 `title`/`key`가 OMR 완료 후에도 그대로다. OMR `COMPLETED` 직후 분석 포함 결과가 한 번에 온다(BR-7 정합).
- **기대 결과 및 완료 기준**
  - [ ] 확정 메타가 파이프라인 전 구간에서 불변
  - [ ] 완료 시 메타+코드+분석 병합 응답 → 코드차트 즉시 활성화

## 5. 키 오입력 경고(비다이아토닉 과다 감지)  ⬜ 미시작  (← BR-28)

### 기능 요약
룰엔진 분석 결과 non-diatonic 코드가 비정상적으로 많으면 "지금 키가 맞나요?" 경고를 띄울 수 있도록, 분석 응답에 키 재확인 신호를 포함한다.

### 상황 설명
사용자가 키를 잘못 입력·확정할 수 있다(BR-26에서 key는 사용자 입력 기본). 키가 틀리면 룰엔진이 대부분의 코드를 non-diatonic으로 태깅해 분석 전체가 이상해지는데, 지금은 이를 감지·안내할 신호가 없다.

### 기능 상세
- **사용자**: 로그인 사용자
- **권한**: 본인 프로젝트
- **시나리오**: 잘못된 키로 분석 완료 → 응답의 경고 신호 확인 → 프론트가 "지금 키가 맞나요?" 모달 표시 → 사용자가 키 수정 → 재분석
- **동작 조건**
  - 분석 응답(BR-17 응답 또는 프로젝트 분석 조회)에 키 경고 필드 포함. `제안`:
    ```jsonc
    "keyWarning": { "suspected": true,
                    "nonDiatonicRatio": 0.62,
                    "suggestedKey": "Bb" }   // nullable — 제안 키 없으면 null
    ```
  - 판정 방식은 재량: 1차는 non-diatonic 비율 임계치로 충분. 코드 진행 기반 Key 분류 모델(pre-trained symbolic)로 최고 확률 키와 불일치 시 `suggestedKey`를 채우는 방식은 **미정**(정확도·지연 실측 후 결정).
- **검증 조건**: 고의로 틀린 키 입력 시 `suspected: true`, 올바른 키에서 `false`.
- **기대 결과 및 완료 기준**
  - [ ] 분석 응답에 `keyWarning` 포함
  - [ ] 틀린 키에서 경고, 맞는 키에서 미경고

## 6. 2-5-1 구간별 "내 릭" 조회  ⬜ 미시작  (← BR-29)

### 기능 요약
코드차트에서 2-5-1(진행 그룹) 구간을 눌렀을 때, 그 진행·키에 해당하는 **내가 저장한 릭**만 조회하는 필터 API.

### 상황 설명
릭 목록은 전체 조회뿐이고 소유자 필터는 BR-10으로 요청돼 있다. 여기에 더해, 차트의 ii-V-I 구간 클릭 시 "그 진행(및 키)에 맞는 내 릭"을 바로 불러오려면 진행·키 기준 서버 필터가 필요하다 — 프론트가 전체 릭을 받아 거르는 방식은 페이지네이션과 어긋난다(BR-11과 같은 문제 구조).

### 기능 상세
- **사용자**: 로그인 사용자
- **권한**: 본인 콘텐츠(소유자 필터와 결합)
- **시나리오**: 코드차트에서 ii-V-I 구간 클릭 → 해당 진행·키의 내 릭 목록 표시 → 선택해 재생/삽입
- **동작 조건**
  - `제안`: `GET /v1/licks?owner=me&progression=ii-V-I&key=C` (+ 페이지네이션). BR-10(owner=me)과 조합 가능해야 한다.
  - 전제: 릭 레코드에 진행 유형·키 메타가 저장돼 있어야 한다. 현 스키마에 없다면 저장 시 받는 필드 추가 필요 — 상세 스키마는 **미정**(정해지면 알려달라, 프론트 저장 폼에 반영).
