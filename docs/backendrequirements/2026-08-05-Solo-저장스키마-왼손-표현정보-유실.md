# 🆕 2차 후속 요청 2건 (신규 — BR-42~44 구현분 검토 결과)

## BR-45 — null 직렬화로 `sheetData` 가 **4.9배** 부푼다 ✅ 완료·배포됨

**기능 요약**
DTO 를 넓힌 대가로 **저장 JSON 과 응답 본문이 5배 가까이 커진다.** 한 줄로 고칠 수 있다.

**상황 설명 (실측 2026-08-05)**
`SoloMapper` 의 `new ObjectMapper()` 는 Jackson 기본값(`Include.ALWAYS`)이라 **null 필드를
전부 기록**한다. 백엔드 전역 Jackson 설정에도 `default-property-inclusion` 이 없어
HTTP 응답도 마찬가지다. 지금도 이미 그렇게 나간다:

```json
{"keys":["b/4"],"duration":"hr","accidentals":null,"tuplet":null,
 "dotted":null,"tie":null,"gliss":null,"beamBreak":null}
```

문제는 **필드 수가 음표 8→35, 마디 2→17 로 늘었다**는 것이다. 실제 최대 크기 솔로
(`Free For All - Wayne Shorter Solo`, 1,449음 · 232마디)로 계산한 결과:

| | 크기 |
|---|---|
| 현재(음표 8필드) | **184 KB** |
| BR-40~44 적용 후(음표 35필드 · 마디 17필드) | **900 KB** |
| 증가 | **4.89배 · +699 KB** |

목록 응답도 같은 비율로 커진다 — `GET /v1/solos?size=60` 이 지금 **4.2 MB** 인데
**약 20 MB** 가 된다. 양손·다중 보표 악보는 `staves` 가 첫 파트를 미러하는 규약이라
한 번 더 곱해진다. `sheet_data_json` 은 TEXT 컬럼이라 DB 도 같이 커진다.

**기능 상세**
- 사용자: 솔로를 조회하는 모든 사용자(특히 모바일 · 목록 화면)
- 동작조건: **null 필드를 직렬화에서 제외**한다.
  ```java
  private static final ObjectMapper MAPPER = new ObjectMapper()
      .findAndRegisterModules()
      .setSerializationInclusion(JsonInclude.Include.NON_NULL);
  ```
  (또는 응답 record 에 `@JsonInclude(NON_NULL)`, 또는 전역
  `spring.jackson.default-property-inclusion: non_null`)
  - ⚠️ **`NON_EMPTY` 가 아니라 `NON_NULL`** 이어야 한다 — `isDrum: false`,
    `withNotation: false` 처럼 **의미 있는 false** 가 살아남아야 한다.
- 무손실인 이유: 신규 필드는 전부 `@Nullable` optional 이고, 프론트는 `undefined` 와
  `null` 을 동일하게(= 해당 표기 없음) 해석한다. 값이 있는 필드는 그대로 나간다.
- 검증조건: 같은 솔로를 저장 → 조회했을 때 **표기 값은 전부 동일**하면서 응답
  바이트가 현재 수준(180 KB 대)으로 돌아온다
- 기대결과: 무손실 저장을 얻으면서 응답·DB 크기는 그대로

상태: ✅ 완료 (2026-08-08 운영 배포·검증)

## BR-46 — Lick 도 sheetData 무손실화 — **Solo 와 완전 동일 범위** ✅ 완료·배포됨

**기능 요약**
백엔드에서 "릭도 할까요?" 물어온 건에 대한 답 — **한다. 범위는 Solo 와 똑같이 전부.**
`domain/lick` 의 sheetData DTO 를 `domain/solo` 와 **필드 단위로 동일**하게 맞춘다.

> **2026-08-05 정정** — 이 문서의 앞선 판(v5·v6)에서 "릭은 발췌라 도돌이·볼타·
> navigation·bracket·anacrusis·rehearsal 은 불필요"라고 범위를 줄였다. **그 판단은
> 틀렸다.** 근거였던 "프론트가 제거한다"는 것은 **솔로 발췌 경로 한 곳**
> (`handleSaveLickFromSelection`)의 동작일 뿐인데 기능 전체로 일반화했다. 실제로는
> 에디터 릭 모드에서 마디 탭(도돌이·볼타·리허설·세로줄·줄바꿈)이 **그대로 열려 있고**,
> 릭 모드에서 비활성화되는 것은 스태프 추가 버튼 **단 하나**다(`EditorPage.tsx` 전체에서
> `mode === 'lick'` 분기는 그 한 곳뿐). 즉 지금도 릭에 볼타를 찍고 저장하면 조용히 사라진다.

**상황 설명**
`domain/lick` 의 DTO 는 `domain/solo` 의 **BR-40 이전 모양 그대로의 복제본**이다 —
`SheetDataRequest` 5필드 · `MeasureRequest` 2필드 · `NoteInfoRequest` 8필드.

**왜 전부인가 — 네 가지**

1. **에디터가 같다.** 릭 모드 제약은 스태프 추가 버튼 하나뿐이다. 아티큘레이션·셈여림·
   꾸밈음·스쿱/폴·보이스2·**마디 탭 전체**를 릭에서도 쓸 수 있다. 지금은 입력은 되는데
   저장이 안 되는 상태다.
2. **뷰어가 같다.** LickCard 도 솔로와 같은 `NoteSheet` 렌더러라 도돌이·볼타도 그린다 —
   데이터만 오면 된다.
3. **솔로 발췌가 릭이 된다.** Solo Database 구간 선택 저장은 음표를 통째로 복사한다
   (`m.notes.map((n) => ({ ...n }))`). 솔로만 표기를 보존하면 **같은 프레이즈가 솔로
   화면과 릭 카드에서 다르게 보인다.**
4. **비대칭의 비용이 필드의 비용보다 크다.** BR-40→46 이 여기까지 온 이유가 바로
   "좁은 DTO 는 쓸 때 싸고 발견할 때 비싸다" 였다. 지금 빼는 필드 하나가 다음 라운드의
   버그 리포트가 된다. **BR-45(NON_NULL)를 적용하면 안 쓰는 필드는 전송 바이트가 0**
   이므로, 범위를 줄여서 아끼는 것이 실질적으로 없다.

**"발췌라 필요 없다"는 논리가 왜 스키마 층에 오면 안 되나**
발췌에서 반복 구조를 떼는 것은 **제품 판단**이고, 이미 그 판단이 일어나는 자리
(`SolosPage.tsx` 의 `sliced`)에서 명시적으로 구현돼 있다. 같은 판단을 **저장 스키마에
한 번 더** 박으면, 나중에 "릭도 도돌이 되게 하자"가 되는 순간 백엔드 변경 + 배포가
다시 필요해진다. 스키마는 "무엇을 담을 수 있나"만 정하고, "무엇을 담을까"는 프론트가
정하게 두는 편이 옳다.

**기능 상세**
- 동작조건: `lick` 의 `SheetDataRequest/Response` · `MeasureRequest/Response` ·
  `NoteInfoRequest/Response` 를 **solo 와 필드 단위로 동일**하게 맞춘다
  (BR-40 · BR-41 · BR-42 · BR-44 전부 + `StaveRequest/Response` 대응).
  `LickMapper` 도 `convertValue` 무손실 변환으로 교체하고, `MeasureRequest.notes` 의
  `@NotEmpty` 를 제거한다(BR-43 과 동일 — 지금 릭 DTO 에도 같은 지뢰가 있다).
- **BR-45(NON_NULL)를 `LickMapper` 에도 함께** — 안 하면 릭 응답도 같은 비율로 부푼다.
- `staves`/`bassMeasures` 도 포함한다. 릭 단일 보표 제한은 프론트 v1 제약이지
  도메인의 진실이 아니다(양손 컴핑 릭은 충분히 있을 수 있고, 에디터 툴팁도
  "릭은 단일 보표만 **저장**됩니다" — 저장의 한계라고 말하고 있다).
- 검증조건: solo 쪽 테스트 2종(`SoloMapperSheetDataTest` · `SheetDataRequestValidationTest`)을
  lick 패키지에 대응 이식해 통과. 에디터 릭 모드에서 볼타·아티큘·셈여림을 넣어 저장 →
  조회 시 그대로. Solo 구간 선택 → 릭 저장 시 원본과 표기 동일.
- 기대결과: **"sheetData 는 무손실"** 이라는 규칙 하나가 solo·lick 양쪽에 똑같이 성립한다

**구조 제안(참고, 강제 아님)**
solo 와 lick 의 sheetData DTO 가 완전한 복제본이라 **같은 버그가 두 번 난다**(BR-40~44
가 그 증거다). 완전 동일 범위로 갈 것이라면 공용 패키지 추출이 자연스럽다 — 다만 두
도메인 다 백엔드 담당자 소유 영역이므로 **판단은 담당자에게 맡긴다.** 지금은 복제로
가고 나중에 뽑아도 된다.

# ✅ 완료 — BR-40 ~ BR-44 (2026-08-05 구현, 재검토 통과)

커밋 `583aaaf`(BR-40/41) + `3e55a48`(BR-42/43/44). 요청한 항목이 **전부 정확히** 반영됐고,
Request ↔ Response 필드 대응도 1:1 로 확인했다. 프론트 `NoteInfo`·`MeasureInfo`·
`NoteSheetData` 와 필드 단위로 대조한 결과 **누락 0건**이다.

| 항목 | 내용 | 확인 |
|---|---|---|
| BR-40 | `bassMeasures` · `staves[]`(`StaveRequest` 신설) · `composer` · `genre` · `accidentalStyle` · `isDrum` | ✅ |
| BR-41 | 음표 표기 23필드 | ✅ |
| BR-42 | 마디 레벨 15필드(`repeatStart` … `tempo`) + `MeasureResponse` 대칭 | ✅ |
| BR-43 | `MeasureRequest.notes` 의 `@NotEmpty` 제거 → 빈 마디 허용. **음표 자체 검증(`keys @NotEmpty`)은 유지** | ✅ |
| BR-44 | `pedalStart` · `pedalEnd` · `textAbove` · `tabStrings` | ✅ |

특히 좋았던 점:

- `SoloMapper` 를 수동 8필드 복사에서 `MAPPER.convertValue(request, SheetDataResponse.class)`
  로 교체한 것 — 유실의 실제 원인이었고, 앞으로 필드를 늘려도 매퍼를 고칠 필요가 없다.
- 하위호환 생성자(5-arg · 8-arg · 2-arg)를 남겨 OMR 등 기존 호출부를 안 깨뜨린 점.
- BR-43 검증을 **jakarta `Validator` 로 직접 돌려** 컨트롤러 `@Valid` 경로를 재현한 점.
  통과 케이스(빈 왼손 마디)와 실패 케이스(`keys: []`)를 **양방향으로** 넣어, 제약을
  풀면서 음표 검증 전파가 살아 있는지까지 확인했다. 요청했던 취지 그대로다.
- 쉼표는 프론트가 자리표시 key 를 항상 채우므로(`restKeyForClef` → `b/4`·`d/3` …)
  `keys @NotEmpty` 유지가 안전하다. 별도 조치 불필요.
