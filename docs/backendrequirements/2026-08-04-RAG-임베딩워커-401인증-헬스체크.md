# 2026-08-04 · RAG 임베딩 워커 401 인증 실패·헬스체크 오탐 요구사항 3건

🏷 **범주(태그):** RAG·화성 검색

**운영에서 RAG 검색이 전면 중단돼 있다.** 채팅은 답을 하지만 코퍼스 근거 없이 LLM 지식만으로
답하고, 출처 인용도 비어 있다. 원인은 임베딩 워커 장애가 아니라 **백엔드 → 워커 호출의 인증 실패
(401)** 다. 색인 자체는 살아 있다(22 docs / 285 chunks).

호출 구조는 `프론트 → 백엔드 → 임베딩 워커` 이고, **끊긴 곳은 두 번째 구간**이다. 프론트는 이
구간에 관여하지 않는다.

> ℹ️ 2026-08-04 실측(운영 서버). 프론트가 채팅 스트림에 `debug: true` 를 보내도록 고친 뒤
> RAG 디버그 블록이 복구돼 에러 원문이 다시 보이게 되면서 확인됐다.

## 1. 백엔드 → 임베딩 워커 인증 복구 (401 Unauthorized)  ⬜ 미시작  (← BR-37) **[최우선]**

### 기능 요약
백엔드가 임베딩 워커를 호출할 때 워커가 요구하는 Bearer 토큰을 실어 보내, RAG 검색을 복구한다.

### 상황 설명
워커는 **모든 `/v1/embed` 요청에 Bearer 토큰을 요구**한다(위 실측 ②). 그런데 운영 백엔드의
호출에는 유효한 토큰이 실리지 않아 전량 401 로 떨어진다.

백엔드 설정·코드상 근거(읽기만 함):

- `application-prod.yml:159-160`
  - `server-url: ${EMBEDDING_SERVER_URL:}`
  - `api-key: ${EMBEDDING_API_KEY:}` — 기본값이 **빈 문자열**, 주석은 *"내부망 호출이면 비워도 됨"*
- `shared/embedding/EmbeddingClient.java:150-152` — `apiKey` 가 비어 있으면
  **`Authorization` 헤더를 아예 붙이지 않는다**

즉 `EMBEDDING_API_KEY` 가 **비었거나(→ 헤더 없음 → "Missing bearer token") 워커 쪽 키와
다르면(→ "Invalid bearer token")** 401 이 된다. 실제 호출 대상이
`https://wrk.jazzify.p-e.kr`(공개 도메인)이므로 **"내부망이면 비워도 됨"이라는 전제가 지금은
성립하지 않는다.**

### 기능 상세
- **사용자**: 전체 사용자(로그인·비로그인 모두 — RAG 채팅 답변 품질에 직결)
- **권한**: 해당 없음(서버 설정)
- **시나리오**: 사용자가 재즈 이론 질문 → 백엔드가 워커로 임베딩 요청 → 코퍼스 검색 성공 →
  근거 문단과 함께 답변 + 출처 각주 표시
- **동작 조건** (`제안` — 아래 중 택1)
  1. **키 주입**: 운영 백엔드 컨테이너에 워커와 **동일한** `EMBEDDING_API_KEY` 를 주입 후 재기동.
     (권장 — 지금 구조 변경 없음)
  2. **내부망 전환**: `EMBEDDING_SERVER_URL` 을 컨테이너 내부 주소
     (`http://jazzify-embedding-worker:8000`)로 바꿔 공개 도메인을 우회.
     ⚠️ 두 컨테이너가 **같은 도커 네트워크**에 있어야 하고, 워커가 내부망 요청에 한해 토큰을
     면제하도록 설정돼 있어야 한다. 그렇지 않으면 401 이 그대로 재현된다.
- **검증 조건**
  1. `POST /api/v1/chat/global/stream` 에 `{"useRag":true,"debug":true}` → 응답 앞머리
     `RAG_DEBUG` 블록의 `status` 가 `connected`, `error` 없음.
  2. 같은 블록의 `chunks` 가 **1개 이상**이고 `total_retrieved > 0`.
  3. 프론트 채팅에서 답변 하단 **출처 각주가 다시 표시**된다.
- **기대 결과 및 완료 기준**:
  - [ ] RAG 디버그 블록 `status: "connected"` (현재 `offline`)
  - [ ] `chunks` 가 채워져 출처 인용 복구
  - [ ] 워커 로그에 401 이 더 이상 남지 않음

## 2. 임베딩 워커 헬스체크가 모델 적재 여부를 반영  ⬜ 미시작  (← BR-38)

### 기능 요약
`(healthy)` 가 "임베딩을 실제로 처리할 수 있음"을 뜻하도록 헬스체크 판정 기준을 고친다.

### 상황 설명
컨테이너는 6일째 `(healthy)` 인데 워커 `/health` 응답은 **`"model_loaded": false`** 다.
지금 헬스체크는 프로세스가 살아 HTTP 200 을 주는지만 보고 **모델 적재를 보지 않는다.**

그래서 운영자가 `docker ps` 로 `(healthy)` 를 보고 "워커는 정상"이라고 판단하게 되는데,
실제로는 임베딩을 수행할 수 없는 상태일 수 있다. 이번 장애에서도 `(healthy)` 때문에 원인 판별이
한 단계 늦어졌다.

### 기능 상세
- **사용자**: 운영자/개발자(장애 진단)
- **권한**: 해당 없음(인프라 설정)
- **시나리오**: 모델 미적재 상태의 워커 → `docker ps` 에 `(unhealthy)` 로 표시 → 즉시 인지
- **동작 조건** (`제안`)
  - `/health` 는 지금처럼 `200` + `model_loaded` 를 그대로 노출하되, **컨테이너 HEALTHCHECK 는
    `model_loaded == true` 일 때만 통과**하도록 한다.
  - 지연 적재(lazy load) 설계라면 기동 시 **워밍업 1회**를 수행해 `model_loaded` 를 올린 뒤
    ready 로 전환하는 방식도 가능하다. 어느 쪽인지는 워커 설계에 달렸다 — **미정**.
- **검증 조건**
  1. 모델 미적재 상태로 기동 → `docker ps` 에 `unhealthy`.
  2. 적재 완료 후 → `healthy`, `/health` 의 `model_loaded: true`.
- **기대 결과 및 완료 기준**:
  - [ ] `model_loaded:false` 인 동안 컨테이너가 `healthy` 로 표시되지 않는다
  - [ ] BR-37 복구 후 실제 임베딩 호출 1회로 모델 적재까지 확인됨

## 3. `/v1/rag/health` 의 `embeddingReachable` 오탐 수정  ⬜ 미시작  (← BR-39)

### 기능 요약
백엔드 RAG 헬스 엔드포인트가 **인증 실패까지 포함해** 임베딩 사용 가능 여부를 판정하게 한다.

### 상황 설명
`GET /api/v1/rag/health` 가 `embeddingReachable: true` 를 반환하는데, 같은 시각 실제 임베딩
호출은 401 로 전량 실패한다. 이 필드가 **도달성(TCP/HTTP 연결)만 보고 인증·정상 응답을 보지
않는 것**으로 보인다.

결과적으로 헬스 엔드포인트가 "정상"이라고 답하는 동안 기능은 죽어 있었다 — 모니터링·알림을 이
값에 걸면 장애를 놓친다.

### 기능 상세
- **사용자**: 운영자/개발자(모니터링·알림)
- **권한**: 현행 유지
- **시나리오**: 임베딩이 401/5xx 로 실패하는 상태 → 헬스 응답이 즉시 비정상으로 표시 → 알림
- **동작 조건** (`제안`)
  - `embeddingReachable` 판정을 **실제 임베딩 1회 호출 성공** 기준으로 바꾼다
    (짧은 더미 텍스트 1건, 타임아웃 짧게, 결과 캐시 수초).
  - 실패 시 `false` 와 함께 **사유를 노출**한다(예: `embeddingError: "401 Unauthorized"`).
    필드명은 `제안` — 다른 이름이어도 무방하다.
- **검증 조건**
  1. 키를 일부러 틀리게 한 상태 → `embeddingReachable: false` + 사유 문자열.
  2. 정상 상태 → `true`, 응답 지연은 수백 ms 이내(캐시 적용).
- **기대 결과 및 완료 기준**:
  - [ ] 401 상태에서 `embeddingReachable` 이 `false`
  - [ ] 실패 사유가 응답에 포함돼 원인 파악이 헬스 응답만으로 가능
