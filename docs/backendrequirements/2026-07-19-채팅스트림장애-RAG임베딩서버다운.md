## 1. 채팅 스트림이 요청 즉시 500(GLOBAL_001)  ✅ 완료 (2026-07-21)

### 기능 요약
`POST /v1/chat/global/stream`(및 `chord-project`/`sheet-project` 스트림)이 정상 스트림 응답을 반환하도록 복구한다.

### 상황 설명
2026-07-19 admin 계정으로 실측한 결과, 채팅 스트림 엔드포인트가 요청 **약 0.03초 만에 즉시** `500 GLOBAL_001 "서버 내부 오류가 발생했습니다."`를 반환한다. `useRag` 값(true/false)과 무관하게 동일하게 실패하며, 임베딩 타임아웃(30초)과 시간대가 전혀 겹치지 않으므로 **RAG와 별개의, 스트림 응답 경로 자체의 장애**다.

- 대조군: 같은 토큰으로 `GET /v1/auth/me`, `GET /v1/chat`(목록 조회)은 모두 `200`. 즉 인증·DB·조회 경로는 정상이고 **스트림 생성 경로만** 깨져 있다.
- 영향: 웹·앱의 "AI에게 질문하기" 채팅이 전혀 동작하지 않는다(빈 응답/에러).

### 기능 상세
- **사용자**: 로그인 사용자(웹·앱 채팅)
- **권한**: 로그인 필요
- **시나리오**: 채팅창에 질문 입력 → `POST /v1/chat/global/stream` → 토큰 스트림 수신 → 화면에 답변 표시
- **동작 조건**
  1. 최소 요청(아래)으로도 `200` + 스트림 본문(text 청크)이 반환돼야 한다. `제안`:
     ```jsonc
     POST /v1/chat/global/stream
     Authorization: Bearer <token>
     { "message": "C장조 ii-V-I 설명해줘", "useRag": false }
     ```
  2. 즉발 500의 서버 스택트레이스를 확인해 원인 제거(예: LLM 클라이언트/스트림 핸들러 초기화 실패, 환경변수·키 누락 등).
  3. `useRag=true` 경로도 임베딩 서버 복구(2번 항목) 후 정상 동작해야 한다.
- **검증 조건**
  - `useRag=false` 최소 요청 → `200`, 스트림에 실제 텍스트 청크 도착.
  - `useRag=true` 요청 → `200`, (임베딩 복구 후) 스트림 앞에 `RAG_DEBUG` 블록 정상 포함.
- **기대 결과 및 완료 기준**
  - [x] `POST /v1/chat/global/stream` 최소 요청이 200으로 스트림 응답 (2026-07-21 확인)
  - [x] GLOBAL_001 즉발 500 재현 안 됨
  - [x] 웹·앱 채팅에서 답변이 실제로 렌더됨

## 2. RAG 임베딩 서버 다운(13.125.60.202:8001) 복구  ✅ 완료 (2026-07-22)

### 기능 요약
RAG 검색이 의존하는 임베딩 서버를 복구해, `GET /v1/rag/search`와 `useRag=true` 채팅이 실제 컨텍스트를 회수하도록 한다.

### 상황 설명
`GET /v1/rag/health`는 `{ status: ok, enabled: true, embeddingConfigured: true, llmConfigured: true, documentCount: 22, chunkCount: 285 }`로 "정상"처럼 보이지만, 이는 **설정값 존재** 여부일 뿐 실제 연결성은 아니다. 실제 검색을 호출하면 다음과 같이 실패한다:

```
GET /v1/rag/search?q=ii-V-I%20progression&n=3
→ RAG_006: "임베딩 서버 요청에 실패했습니다. - connection timed out after 30000 ms: /13.125.60.202:8001"
```

임베딩 서버 `13.125.60.202:8001`은 외부에서 직접 접속해도 8초 내 무응답(완전 다운)이다. 코퍼스(문서 22개·청크 285개)는 존재하므로 **임베딩 서버만 살아나면 RAG 검색이 복구**된다.

### 기능 상세
- **사용자**: 로그인 사용자(RAG 검색·RAG 채팅)
- **권한**: 로그인 필요
- **시나리오**: RAG 질문 → 서버가 임베딩 서버로 쿼리 임베딩 요청 → 벡터 검색 → 관련 청크 회수 → 답변 근거로 사용
- **동작 조건**
  1. 임베딩 서버(`13.125.60.202:8001`) 프로세스 재기동 및 상시 가동 보장.
  2. `GET /v1/rag/search?q=...`가 `RAG_006` 없이 검색 결과(청크 배열)를 반환.
  3. `GET /v1/rag/health`가 설정값뿐 아니라 **실제 임베딩 서버 연결성**까지 반영하도록 개선(권장) — 현재 다운 상태에서도 `status: ok`로 나와 오탐.
- **검증 조건**
  - `GET /v1/rag/search?q=ii-V-I&n=3` → 200 + 청크 결과.
  - `useRag=true` 채팅 스트림 → `RAG_DEBUG.status = connected` + 회수 청크 표시.
  - `GET /v1/rag/health` → 임베딩 서버 실제 다운 시 `ok`가 아닌 상태로 표기.
- **기대 결과 및 완료 기준**
  - [x] 임베딩 서버 재가동, `/v1/rag/search` 정상 응답 (2026-07-22 확인 — It Could Happen to You·Autumn Leaves 청크 회수)
  - [x] `useRag=true` 채팅에서 RAG 컨텍스트 실제 회수 (RAG_DEBUG에 queries·chunks 실제 데이터, error 사라짐)
  - [ ] health 엔드포인트가 임베딩 연결성을 반영(오탐 제거) — **미해결(잔여)**: 다운 중에도 `status: ok`로 나오는 오탐은 아직 개선 안 됨

> 2026-07-22 참고: 임베딩 서버 IP가 `54.180.103.153`로 교체된다는 공지가 있었으나, 07-21까지는 백엔드가 옛 IP(`13.125.60.202`)로 계속 요청해 타임아웃이 지속됐다. 07-22 재점검 시 검색·RAG 채팅이 모두 정상 복구됨을 확인했다.
