## 1. 음원 분리(Stem Separation) 추론 API  ⬜ 미시작  (← BR-3)

### 기능 요약
업로드한 곡을 스템(보컬/드럼/베이스/기타 등)으로 분리하는 서버 추론 API.

### 상황 설명
`/stems` 페이지는 프론트가 **이미 완성**(업로드·믹서·재생·다운로드 실제 동작)돼 있으나, 정작 "분리"는 브라우저에서 EQ 대역으로 흉내 낸 **데모**다(진짜 AI 분리 아님).

### 기능 상세
- **사용자**: 로그인 사용자
- **권한**: 로그인
- **시나리오**: 곡 업로드 + 스템 수 선택(2/4/6) → 잡 생성 → 진행률 폴링 → 완료 시 스템별 URL·zip 다운로드
- **동작 조건**
  - `제안` 요청/응답:
    ```jsonc
    POST /v1/stems            // multipart: file + preset(2|4|6)
    → { "jobId": "abc123" }

    GET  /v1/stems/{jobId}
    → { "status":"RUNNING|COMPLETED|FAILED", "progress":0.62,
        "stems": { "vocals":"<presigned url>", "drums":"...", ... },
        "zipUrl":"<presigned url>", "expiresAt":"2026-07-12T00:00:00Z" }
    ```
  - 잡 큐 + 진행률 보고. 스토리지 **만료 정책 필수**(원본·결과 자동 삭제). (분리 엔진/GPU 등 내부 구현은 백엔드 재량)
- **검증 조건**: 만료 시각 이후 URL이 죽는다.
- **기대 결과 및 완료 기준**
  - [ ] 5분짜리 곡이 실패 없이 분리되고 스템별 URL 수신
  - [ ] 만료 후 URL 무효

> 프론트 연동: `lib/stems/mockSeparate.ts`의 `separate()` 함수 하나만 API 호출로 교체(페이지·믹서·다운로드 무수정).

#### 구현 참고 (비계약 · 백엔드 재량 — 옛 `음원분리_백엔드 요구사항.md` 흡수본)

아래는 계약이 아니라 **구현 힌트**다. API 형태는 위 `동작 조건`이 기준이고, 여기서는 권장 스택·상세 파라미터·워커 스니펫만 보강한다.

**분리 엔진 선택**

| 방식 | 품질 | 비고 |
|---|---|---|
| **Demucs v4 (htdemucs / htdemucs_6s)** | 업계 최고 (SDR ~9dB) | **권장.** PyTorch, MIT. `htdemucs_6s`가 보컬/드럼/베이스/기타/피아노/기타악기 6-stem 지원 |
| Spleeter (Deezer) | 중간 | TF1 기반, 유지보수 정체. 비권장 |
| Open-Unmix | 중간 | 연구용 기준선 |
| 브라우저 WASM/onnx | 낮음·느림 | 데모 이상 불가 (현 프론트 데모가 이 역할) |

- GPU 필수는 아니나 강력 권장: 3~4분 곡 기준 GPU(T4) ~30초, CPU 5~15분.
- 스프링 서버에서 직접 돌리기보다 **별도 Python 워커(FastAPI/Celery)**로 분리하고 스프링은 접수/조회/저장만 담당하는 구성 권장. GPU 없으면 Replicate/Modal 등 GPU 서버리스로 워커만 외주 가능.

**권장 아키텍처**

```
브라우저 ──(1) 업로드──▶ Spring API ──(2) 잡 큐──▶ Python 분리 워커 (Demucs, GPU)
   ▲                        │                          │
   └──(4) 폴링/스트림────────┘◀──(3) 스템 파일 저장─────┘ (S3/로컬 스토리지)
```

- 분리는 수십 초~수 분 걸리는 **비동기 작업**. 동기 HTTP 응답으로 처리하지 말 것.
- 폴링(간단) 또는 SSE(진행률 % 필요 시) 택1. 프론트는 폴링 기준 구현 예정, SSE 오면 갈아탄다.

**요청/응답 상세 보강**
- `POST /v1/stems` (multipart): `file`(wav·mp3 필수, m4a/ogg/flac 지원 시 명시) + `preset`
  - `2` = vocals / accompaniment(MR) — Demucs `--two-stems=vocals`
  - `4` = vocals / drums / bass / other (htdemucs 기본)
  - `6` = vocals / drums / bass / guitar / piano / other (htdemucs_6s)
  - 응답 `202`: `{ "jobId": "stem_8f3a...", "status": "QUEUED" }`
  - 제한: 파일 최대 크기(프론트 현재 200MB 가드)·길이(예: 15분)·사용자별 동시 잡 1개·일일 쿼터 — **정책 값을 정해서 알려달라**(프론트 에러 문구에 반영).
- `GET /v1/stems/{jobId}` 응답의 스템 `id`는 위 preset 고정 문자열 사용(프론트 아이콘/색 매핑). `progress`는 있으면 사용, 없으면 무시.
- (선택) `GET /v1/stems/{jobId}/mix?gains=vocals:0,drums:1,bass:0.8&format=mp3` — "현재 상태로 저장"의 mp3 출력. WAV 믹스다운은 프론트가 OfflineAudioContext로 자체 처리하므로 mp3/용량 절약이 필요할 때만. 미구현이어도 프론트는 WAV 폴백.
- (선택) `DELETE /v1/stems/{jobId}` — 잡/파일 삭제.

**파일/스토리지 요구**
- 스템 산출물: WAV(원본 샘플레이트) 기본. mp3(320k) 변환본도 함께 주면 모바일 유리(ffmpeg 한 줄).
- zip 패키징: "모든 트랙 저장"용 `zipUrl`을 **백엔드가 제공**(프론트에 zip 라이브러리 없음 — 현 데모는 순차 다운로드 폴백).
- 보존 정책: 결과물 대용량 → 만료(예: 24~72h) + `expiresAt` 반환, 만료 후 조회 시 `410 Gone`.
- 저장: S3 호환 스토리지 권장, presigned URL로 프론트 직접 다운로드(스프링 경유 프록시 금지 — 대역폭).

**인증/보안**
- 기존 Bearer 토큰 그대로(`Authorization: Bearer <access>`), 잡은 소유자만 조회.
- 업로드 검증: magic bytes로 실제 오디오 확인(확장자 신뢰 금지), ffprobe로 길이/코덱 검사.
- 저작권 고지 문구는 프로덕트 결정(프론트 표시 위치는 준비됨).

**워커 구현 참고 (Python)**

```python
# pip install demucs  (torch 포함)
from demucs.separate import main as demucs_run
# 4-stem: htdemucs / 6-stem: htdemucs_6s / 2-stem: htdemucs --two-stems=vocals
demucs_run(["-n", "htdemucs_6s", "--mp3", "-o", out_dir, in_path])
```

- 2-stem은 `--two-stems=vocals` 로 vocals/no_vocals 산출.
- 긴 파일은 `--segment` 로 메모리 제어. GPU 메모리 8GB면 기본값 충분.
- 진행률은 `demucs.api.Separator` 콜백으로 세그먼트 진행률 취득 가능.

**연계 예정 — LLM 채팅 명령 연동**: 인트로 채팅의 "이 파일 스템 분리해줘 / 피아노만 빼줘" 명령은 프론트 rule-based 인텐트 감지 후 **동일한 `POST /v1/stems`를 호출**하는 구조라, 위 API가 완성되면 백엔드 추가 작업 없이 프론트에서 처리 가능. 단 "피아노만 제거한 한 파일" 같은 **부분 믹스 산출**이 필요해지면 `GET .../mix`가 필수가 된다.

## 2. YouTube 온셋 추출 API  ⬜ 미시작  (← BR-15)

### 기능 요약
YouTube URL에서 온셋/멜로디를 추출하는 API.

### 상황 설명
`POST /v1/onset/suggest`가 없어 YouTube 채보 페이지는 **mock JSON**(영상 6개분)으로만 동작한다.

### 기능 상세
- **사용자**: 로그인 사용자
- **권한**: 로그인
- **시나리오**: YouTube URL 입력 → 잡 생성 → 폴링 → 온셋/멜로디 결과 수신
- **동작 조건**: 유튜브 URL → 온셋/멜로디 추출. 오래 걸리므로 **비동기 잡 + 폴링** 권장. 응답 포맷은 프론트 mock 스키마를 그대로 따르면 된다.
- **검증 조건**: 실제 영상에서 온셋 결과가 mock 스키마 형태로 온다.
- **기대 결과 및 완료 기준**
  - [ ] URL → 온셋 결과(mock 스키마 호환)

> 미정: 정확도 목표·지원 영상 길이 상한 등은 추후 합의.
