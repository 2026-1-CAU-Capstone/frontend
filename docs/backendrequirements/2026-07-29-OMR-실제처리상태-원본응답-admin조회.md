# 2026-07-29 · OMR 실제 처리 상태·원본 응답 admin 조회 요구사항 2건

🏷 **범주(태그):** 미디어 추론

내 코드차트(및 악보·솔로·릭)에 악보를 넣었을 때, **OMR 서버가 실제로 뱉는 상태와 원본 응답**을
운영자가 확인할 방법이 없다. 프론트가 볼 수 있는 건 `PENDING`/`PROCESSING`/`COMPLETED`/`FAILED`
네 글자와 `progress` 숫자뿐이라, 문제가 생겨도 **어느 단계에서 왜 막혔는지 알 수 없다.**

> ℹ️ 문서서버 렌더러가 여러 줄 코드블록을 깨뜨려서(줄바꿈 뭉개짐), API 계약을 **표**로 적었다.

## 진행 현황
범례: ✅ 완료 · 🟡 진행중 · ⬜ 미시작
- ⬜ 1. OMR 처리 상태 admin 조회 API (← BR-35)
- ⬜ 2. OMR 원본 응답 admin 조회 API (← BR-36)

## 1. OMR 처리 상태 admin 조회 API  ⬜ 미시작  (← BR-35)

### 기능 요약

관리자가 `publicId` 하나로 **해당 OMR 작업의 실제 처리 상태**(페이지별 + OMR 서버 실시간 단계)를
조회하는 admin 전용 API.

### 상황 설명

현재 프론트가 쓸 수 있는 건 `GET /v1/{리소스}/{publicId}/omr-status` 뿐이고, 여기서 오는 정보는
`status` · `progress` · `totalPages` · `completedPages` · `failureReason` 가 전부다.

문제는 이 정보로는 **진단이 안 된다**는 점이다.

- `PROCESSING` 에서 멈춰 있을 때, OMR 서버가 실제로 돌고 있는 건지 / 콜백이 유실된 건지 구분 불가
- `FAILED` 인데 `failureReason` 이 비어 있으면 원인 추적 불가
- 다중 페이지 PDF에서 **어느 페이지가** 막혔는지 알 수 없음

반면 OMR 서버(MusicVision)는 `GET /omr/jobs/{job_id}` 로 `stage`(예: `cell_ocr`),
`message`(예: "Reading chart cells (12/30)"), `current_step`/`total_steps`, `error`,
`callback_error` 까지 이미 제공한다. **백엔드는 이 API를 이미 호출하고 있다**
(`OmrClient.fetchJobStatus`). 다만 그 결과가 **밖으로 나오지 않아** 운영자가 볼 수 없다.

지금은 이걸 보려면 **서버에 SSH로 들어가야 한다**고 안내받는 상황이다. 장애 대응이 사실상 막혀 있다.

### 기능 상세

- **사용자**: 관리자(admin)
- **권한**: 로그인 필요 + admin 등급. 일반 사용자에게 노출하지 않는다
- **시나리오**:
  1. 사용자가 "이 악보가 인식이 안 된다"며 코드차트/악보를 제보한다
  2. 운영자가 admin 화면(`/admin/omr`)에 그 `publicId` 를 넣는다
  3. 배치 전체 상태 + **페이지별 상태** + **OMR 서버 실시간 단계**가 한 화면에 나온다
  4. 어느 페이지가 어느 단계에서 막혔는지 즉시 판단한다
- **동작 조건** (외부 API 계약 — `제안`):

  **`GET /v1/admin/omr/jobs/{publicId}`**

  | 응답 필드 | 타입 | 설명 |
  | --- | --- | --- |
  | `publicId` | string(uuid) | 조회한 리소스 식별자 |
  | `domain` | string | `SOLO` / `LICK` / `CHORD_PROJECT` / `SHEET_PROJECT` |
  | `status` | string | 배치 전체 상태 |
  | `totalPages` / `completedPages` | int | 페이지 진행 |
  | `createdAt` / `updatedAt` | datetime | 배치 생성·갱신 시각 |
  | `pages[]` | array | 페이지별 상세(아래) |

  | `pages[]` 필드 | 타입 | 설명 |
  | --- | --- | --- |
  | `pageNumber` | int | 1부터 |
  | `omrJobId` | string | **OMR 서버의 실제 job_id** |
  | `status` | string | 페이지 상태 |
  | `progress` | int | 0~100 |
  | `failureReason` | string/null | 실패 사유 |
  | `imageFilename` | string | 제출한 이미지 파일명 |
  | `retryCount` | int/null | 결과 회수 재시도 횟수 |
  | `nextRetryAt` | datetime/null | 다음 재시도 예정 시각 |
  | `live` | object/null | **OMR 서버 실시간 상태**(아래). 조회 실패 시 `null` |

  | `live` 필드 | 타입 | 설명 |
  | --- | --- | --- |
  | `status` | string | OMR 서버 상태(`queued`/`processing`/`completed`/`failed`/`not_found`) |
  | `stage` | string/null | 내부 처리 단계 (예: `cell_ocr`) |
  | `message` | string/null | 사람이 읽는 진행 메시지 |
  | `progress` | int/null | 0~100 |
  | `error` | string/null | 실패 원인 |

  - `live` 조회는 **선택적으로** 동작해야 한다. OMR 서버가 죽어 있어도 저장된 값은 반환되어야 하며,
    `live` 만 `null` 이 되어야 한다(전체 500 금지).
  - `live` 를 매번 호출하는 게 부담이면 쿼리 파라미터(예: `?live=true`)로 분리해도 좋다. **미정** — 백엔드 판단.

- **검증 조건**:
  - 처리 중인 다중 페이지 PDF를 조회 → 페이지별로 서로 다른 `status`/`progress` 가 보인다
  - 일부러 OMR 서버를 내린 뒤 조회 → 저장값은 그대로 오고 `live` 만 `null` 이다
  - 일반 사용자 토큰으로 호출 → `403`
  - 존재하지 않는 `publicId` → `404`
- **기대 결과 및 완료 기준**:
  - [ ] `GET /v1/admin/omr/jobs/{publicId}` 가 admin 권한으로 동작한다
  - [ ] 응답에 `omrJobId` 와 페이지별 상태가 포함된다
  - [ ] OMR 서버 실시간 `stage`/`message` 가 `live` 로 포함된다
  - [ ] OMR 서버 장애 시에도 200 + `live: null` 로 응답한다
  - [ ] 비-admin 접근이 차단된다

## 2. OMR 원본 응답 admin 조회 API  ⬜ 미시작  (← BR-36)

### 기능 요약

관리자가 **OMR 서버가 실제로 반환한 원본 데이터**(결과 JSON / MusicXML)를 가공 없이 그대로
내려받아 확인하는 admin 전용 API.

### 상황 설명

인식 결과가 이상할 때(코드가 엉뚱한 마디에 붙거나, 왼손이 사라지거나, 코드가 비어 있거나)
**원본을 봐야** 어디서 틀어졌는지 판단할 수 있다. 지금은 그 원본을 볼 수단이 없다.

- 프론트가 받는 건 이미 백엔드가 **가공한** 결과다 — 원본과 대조가 불가능하다
- 따라서 "OMR이 잘못 읽은 것"인지 "백엔드 변환이 잘못된 것"인지 **책임 구간을 못 가른다**
- 실제로 과거 요구사항(BR-33 양손 유실, #20 그랜드스태프)에서 이 구분 때문에 시간이 크게 소모됐다

확인 결과 원본 데이터는 **이미 DB에 보존되고 있다**(페이지별 결과 JSON·MusicXML). 즉 새로
수집할 필요 없이 **꺼내주기만** 하면 된다.

### 기능 상세

- **사용자**: 관리자(admin)
- **권한**: 로그인 필요 + admin 등급
- **시나리오**:
  1. 운영자가 인식 품질 이상을 발견한다
  2. admin 화면에서 해당 페이지의 "원본 보기"를 누른다
  3. OMR 서버가 준 결과 JSON / MusicXML 원문이 그대로 표시된다
  4. 원본과 화면 결과를 대조해 OMR 문제인지 변환 문제인지 판정한다
- **동작 조건** (외부 API 계약 — `제안`):

  **`GET /v1/admin/omr/jobs/{publicId}/pages/{pageNumber}/raw`**

  | 응답 필드 | 타입 | 설명 |
  | --- | --- | --- |
  | `publicId` | string(uuid) | 리소스 식별자 |
  | `pageNumber` | int | 페이지 번호 |
  | `omrJobId` | string | OMR 서버 job_id |
  | `resultJson` | string/null | **OMR 서버 원본 결과 JSON 문자열** (가공 금지) |
  | `musicXml` | string/null | **원본 MusicXML 문자열** (가공 금지) |
  | `failureReason` | string/null | 실패 사유 |

  - 두 필드 모두 **문자열 원문 그대로** 반환한다. 파싱·정규화·필드 선별을 하지 않는다.
  - 용량이 크다(실측 MusicXML 62KB, 코드 배정 JSON 56KB 사례). 페이지 단위로만 반환하고
    배치 전체를 한 번에 내려주지 않는다.
  - 저장된 값이 없으면 해당 필드는 `null` (404 아님).

- **검증 조건**:
  - 완료된 다중 페이지 작업의 2페이지를 조회 → 그 페이지의 원문만 온다
  - 반환된 `musicXml` 이 유효한 MusicXML로 파싱된다
  - 반환된 `resultJson` 이 유효한 JSON으로 파싱된다
  - 일반 사용자 토큰으로 호출 → `403`
- **기대 결과 및 완료 기준**:
  - [ ] `GET /v1/admin/omr/jobs/{publicId}/pages/{pageNumber}/raw` 가 admin 권한으로 동작한다
  - [ ] `resultJson` · `musicXml` 이 **가공 없이** 원문으로 반환된다
  - [ ] 페이지 단위로만 응답한다(배치 일괄 반환 없음)
  - [ ] 비-admin 접근이 차단된다

## 참고 · 조율 필요 사항

- **왜 프론트에서 직접 못 하는가**: OMR 서버 호출에는 `X-OMR-API-Key` 가 필요하고, 이 키가
  브라우저에 노출되면 안 된다. 또한 OMR 서버는 인터넷에 공개돼 있지 않다(SSH가 필요하다는 것 자체가
  내부망이라는 뜻). 따라서 **백엔드 경유가 유일한 경로**다.
- **왜 OMR 팀의 신규 API가 필요 없는가**: 필요한 상태 API(`GET /omr/jobs/{job_id}`)는 이미 있고
  백엔드가 이미 호출 중이다. 부족한 건 **그 결과를 admin에게 노출하는 백엔드 엔드포인트**뿐이다.
- ⚠️ **컨트롤러 위치는 조율 필요**: OMR 작업 도메인 패키지는 2026-07-22 담당 경계 합의 문서에
  포함돼 있지 않은 신설 영역이고, 코드/악보/솔로 도메인(백엔드 담당자 소유)이 이를 참조한다.
  **어디에 admin 컨트롤러를 두는지는 백엔드 담당자와 합의 후 진행**한다.
- **프론트 준비 상태**: admin 화면 `/admin/omr` 은 이미 구현돼 있다(진행률·처리 기록·publicId 조회).
  위 두 API가 생기면 **바로 붙일 수 있다.**
