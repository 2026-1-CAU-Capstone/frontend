## 1. 온라인 화성 분석 API  ✅ 완료  (← BR-17)

### 기능 요약
임의의 코드 진행을 **질문 시점에** 분석해 도수·기능·`ii-V-I` 그룹·모호성 점수를 돌려주는 API.

### 상황 설명
화성 분석(룰 기반 파이썬 엔진)이 지금은 **batch(미리 한 번 계산)** 로만 쓰인다: 개발자 PC에서 batch → 결과 JSON을 코드에 수동 복붙 → 배포. 즉 **사용자가 질문하는 순간에는 룰엔진이 돌지 않고**, 모호성 점수도 그때 계산되지 않는다. 결과: (1) 사용자가 만든 곡(에디터·iReal·OMR)은 `chord.analysis`가 비어 답변이 얕다, (2) 모호성 기반 분기(RAG)의 입력값 자체가 없다, (3) 운영이 수동이다.

### 기능 상세
- **사용자**: 로그인 사용자(임의 곡 분석)
- **권한**: 로그인
- **시나리오**: 에디터/iReal/OMR로 만든 코드 진행 → 분석 API 호출 → 도수·기능·그룹·모호성 부여 → AI 답변/화면에 활용
- **동작 조건**
  - `제안` 요청/응답:
    ```jsonc
    POST /v1/analysis/chords
    { "key": "C", "timeSignature": "4/4",
      "chords": [ { "bar":1,"beat":1,"symbol":"Dm7" }, { "bar":1,"beat":3,"symbol":"G7" }, { "bar":2,"beat":1,"symbol":"Cmaj7" } ] }
    ```
    ```jsonc
    // 응답 — 프론트 LeadSheetChordAnalysis 모양이면 무수정 연동
    { "chords": [ { "bar":1,"beat":1,"symbol":"Dm7",
        "analysis": { "degree":"ii","isDiatonic":true,
          "functions":[{"function":"SD","confidence":1.0}],
          "groupMemberships":[{"groupType":"ii-V-I","role":"ii"}],
          "secondaryDominant":null,"modalInterchange":null,
          "ambiguityScore":0.12 } } ] }
    ```
  - 운영: 같은 진행이면 **캐시**(진행 해시→결과), DB에 없는 곡이면 **온디맨드**로 그 자리에서 분석·저장. (기존 batch는 두고 온디맨드를 얹는 방식)
- **검증 조건**: 같은 진행 재요청 시 캐시 히트(응답 급감). `ambiguityScore`가 응답에 포함(RAG 입력).
- **기대 결과 및 완료 기준**
  - [x] 에디터 임의 진행에도 도수·기능·`ii-V-I` 그룹이 붙는다
  - [x] 재요청 캐시 히트
  - [x] `ambiguityScore` 포함

**검증(2026-07-29)**: `POST /v1/analysis/chords` 실호출 200 — 응답에 `degree`/`isDiatonic`/`functions`/`groupMemberships`/`ambiguityScore` 모두 포함. 화성 엔진이 파이썬 batch에서 자바로 포팅됨(`domain/analysis/service/implementation/` 17개 컴포넌트). 캐시 실측 0.150s → 0.059s.

> 응답을 프론트 `LeadSheetChordAnalysis` 모양으로 맞추면 `buildChordContext`를 한 줄도 안 고치고 재사용 가능.

## 2. OMR 완료 후 화성 분석 자동 실행  ✅ 완료  (← BR-7)  [백엔드+OMR]

### 기능 요약
코드차트 OMR이 완료되면 화성 분석이 자동으로 실행돼, 분석 조회가 한 번에 성공하게 한다.

### 상황 설명
코드차트 OMR 상태가 `COMPLETED`인데 `GET /v1/chord-projects/{id}/analysis`를 부르면 **400 `CHORD_PROJECT_005`(분석 미실행)** 가 온다. 사용자는 "인식 완료"를 봤는데 분석 화면이 에러다. 지금은 프론트가 몰래 `POST /analyze`를 대신 눌러 덮고 있다.

### 기능 상세
- **사용자**: 로그인 사용자
- **권한**: 본인 프로젝트
- **시나리오**: 악보 사진 업로드 → OMR 완료 → 분석 화면 진입 → 분석 결과 바로 표시
- **동작 조건**: 둘 중 하나 —
  - (A) OMR이 `COMPLETED`되는 순간 **분석 자동 트리거**
  - (B) `GET /analysis`를 **lazy-run** 으로: 분석 없으면 그 자리에서 돌려 결과 반환
  - (OMR 측: `COMPLETED` 신호/훅을 백엔드가 받을 수 있게 연동)
- **검증 조건**: OMR 완료 직후 `GET /analysis`가 **한 번에 200**.
- **기대 결과 및 완료 기준**
  - [x] OMR 완료 후 분석 조회 200(400 self-heal 불필요)

**검증(2026-07-29)**: (B) lazy-run 으로 구현됨 — `ChordProjectService.getAnalysisResult()` 가 `lastAnalyzedAt == null` 이면 그 자리에서 분석을 실행한다. 옛 에러코드 `CHORD_PROJECT_005` 는 더 이상 어디서도 throw 되지 않는다. 기존 OMR 완료 프로젝트 4건 전부 `GET /analysis` 한 번에 200.

> 프론트 완화(적용됨): 폴러가 COMPLETED 감지 시 `POST /analyze` 자동 호출 + 400 self-heal + 중복 제거.

## 잔여(후속)

본 요구사항 2건은 완료됐으나, 아래는 남은 후속 과제다.

- **분석 캐시가 인메모리 LRU(max 256)** — 재기동 시 소실되고 인스턴스 간 공유되지 않는다. DB 영속이 아니므로 다중 인스턴스/재배포 환경에서는 캐시 히트율이 떨어진다.
- **OpenAPI 설명문이 낡음** — `GET /v1/chord-projects/{publicId}/analysis` 의 스펙 설명에 `ChordProjectControllerSpec.java:242-243` 기준 아직 "분석이 한 번도 실행되지 않은 경우 에러를 반환합니다"가 남아 있다. 실제 동작(lazy-run)과 **반대**라, 스펙만 보면 이 기능이 미구현인 것으로 오독된다. 설명문 갱신 필요.
- **프론트의 self-heal 우회 코드가 불필요해짐** — `MyChordChartsPage.tsx:2250-2257`, `ChordPage.tsx:1425-1435`, `api/chordProjects.ts:124` 의 400 self-heal 로직은 이제 죽은 경로다. 제거 가능(프론트 작업).
