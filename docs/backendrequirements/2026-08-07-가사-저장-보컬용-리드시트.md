# 2026-08-07 · 가사(lyrics) 저장 — 보컬용 리드시트 3건

🏷 **범주(태그):** 콘텐츠·라이브러리·스토리지

보컬 사용자를 위해 악보에 **가사**를 붙인다. 프론트는 MusicXML `<lyric>` 파싱을 완료했고(아래 §0 실측), 이제 그 결과를 저장·복원할 백엔드가 필요하다. 현재 `NoteInfoRequest` 는 8개 필드(`keys, duration, dotted, accidentals, tie, gliss, tuplet, beamBreak`)만 정의해 **가사를 보내면 조용히 사라진다**(BR-34 와 같은 원인).

## 진행 현황
범례: ✅ 완료 · 🟡 진행중 · ⬜ 미시작
- ⬜ 1. 음표별 가사 음절 저장 (← BR-47)
- ⬜ 2. 솔로 목록/검색에 가사 보유 여부 노출 (← BR-48)
- ⬜ 3. **코드차트** 마디별 가사 저장 (← BR-49)

## 0. 실측 근거 — MusicXML 가사 파싱 (프론트 완료)

`public/data/example/beautiful-love-lead-sheet-with-lyrics.mxl` 를 실제 파서로 읽어 **원본 XML 과 1:1 대조**했다.

| 항목 | 원본 XML | 파서 출력 | 결과 |
|---|---|---|---|
| 가사가 달린 음표 | 46 | 46 | ✅ |
| 음절(`<lyric>`) 총수 | 76 | 76 | ✅ |
| 절(verse) 번호 | 1·2 (46 / 30) | 1·2 | ✅ |
| `syllabic` 분포 | single 40 · begin 14 · end 13 · middle 9 | 동일 | ✅ |
| 멜리스마 `<extend/>` | 4 | 4 | ✅ |
| **음절 단위 완전 일치** | — | **76/76** | ✅ **100%** |

복원된 1절: *"Beau-ti-ful love, you're all a mys-ter-y, beau-ti-ful love. what have you done to me? …"*

**프론트 데이터 모델** (`frontend/src/data/sampleMelody.ts`):
```ts
interface LyricSyllable {
  verse: number;                                     // 절 번호(1부터) = MusicXML <lyric number>
  text: string;                                      // 음절 텍스트 ('Beau', 'love,')
  syllabic?: 'single' | 'begin' | 'middle' | 'end';  // 하이픈 판단
  extend?: boolean;                                  // 멜리스마(<extend/>)
}
interface NoteInfo { /* … */ lyrics?: LyricSyllable[]; }
```
한 음표에 **여러 절**이 붙을 수 있어 배열이다(위 예시는 30음표가 1·2절 동시 보유).

## 1. 음표별 가사 음절 저장  ⬜ 미시작  (← BR-47)

### 기능 요약
`sheetData.measures[].notes[].lyrics` (음절 배열)를 손실 없이 저장·반환한다.

### 상황 설명
보컬 사용자는 악보를 보며 가사를 함께 읽어야 한다. 가사는 **음표에 붙는 정보**다 — 어느 음에 어느 음절이 오는지가 곧 리듬이므로, 곡 단위 텍스트 한 덩어리로는 대체할 수 없다(멜리스마·하이픈·절 구분이 사라진다).
현재 `NoteInfoRequest` 에 `lyrics` 가 없어 POST/PUT 으로 보내도 역직렬화에서 **탈락**한다. 저장은 HTTP 200 으로 성공 응답하므로 사용자는 다시 열어봐야 유실을 안다(BR-34 와 동일한 실패 양상).

### 기능 상세
- **사용자**: 보컬·일반 사용자(솔로/악보 프로젝트 작성·열람)
- **권한**: 로그인 필요(본인/관리자)
- **시나리오**: 가사 포함 MusicXML 업로드 → 파싱된 가사가 악보에 표시 → 저장 → 다시 열어도 가사 유지 → 에디터에서 음절 편집·저장
- **동작 조건**: `sheetData` 는 프론트 렌더러 전용 페이로드이므로 **해석 없이 그대로 저장·반환**하면 된다.
  - `제안` — `NoteInfoRequest`/`NoteInfoResponse` 에 필드 추가:
    ```jsonc
    "lyrics": [
      { "verse": 1, "text": "Beau", "syllabic": "begin" },
      { "verse": 2, "text": "love,", "syllabic": "single", "extend": true }
    ]
    ```
    · `verse` 정수(1부터) · `text` 문자열 · `syllabic` `single|begin|middle|end`(nullable) · `extend` boolean(nullable)
  - ⚠️ **BR-34(sheetData 전면 pass-through)가 채택되면 이 항목은 자동 해결**된다. 별도 구현 대신 BR-34 로 묶어도 무방하다.
- **검증 조건**: 위 §0 파일을 업로드해 저장 → `GET` 으로 되받아 **가사 달린 음표 46개·음절 76개가 필드까지 바이트 동일**한지 확인.
- **기대 결과 및 완료 기준**:
  - [ ] `NoteInfoRequest`/`Response` 에 `lyrics` 포함
  - [ ] POST/PUT → GET 왕복에서 절·텍스트·`syllabic`·`extend` 전부 보존
  - [ ] 가사 없는 기존 데이터는 영향 없음(필드 부재 유지)

## 2. 솔로 목록/검색에 가사 보유 여부 노출  ⬜ 미시작  (← BR-48)

### 기능 요약
솔로 목록 응답에 **가사 포함 여부** 플래그를 넣고, 그 조건으로 필터링할 수 있게 한다.

### 상황 설명
보컬 사용자는 "가사가 있는 곡"만 빠르게 찾고 싶다. 지금은 목록 API 가 `sheetData` 를 내려주지 않으므로, 가사 유무를 알려면 곡마다 상세를 받아야 한다(N+1). 목록 단계에서 걸러야 한다.

### 기능 상세
- **사용자**: 보컬·일반 사용자
- **권한**: 목록 조회 권한과 동일
- **시나리오**: 솔로 데이터베이스에서 "가사 있는 곡만" 토글 → 해당 곡만 표시
- **동작 조건**:
  - `제안` — 목록 응답 항목에 `hasLyrics: boolean` 추가(저장 시점에 서버가 `sheetData` 를 훑어 계산·캐시).
  - `제안` — `GET /v1/solos` 에 `hasLyrics=true` 쿼리 파라미터로 필터.
  - 절 개수까지 필요하면 `lyricVerseCount: number` 추가(미정 — 프론트 UI 확정 후 요청).
- **검증 조건**: 가사 포함 솔로 1건·미포함 1건을 저장한 뒤 목록 조회 → 플래그가 각각 true/false, 필터 적용 시 1건만 반환.
- **기대 결과 및 완료 기준**:
  - [ ] 목록 응답에 `hasLyrics` 포함
  - [ ] `hasLyrics` 필터 동작
  - [ ] 기존 데이터는 false 로 안전하게 계산

---

> ⚠️ 의존: **BR-47 이 없으면 가사는 저장되지 않는다.** 프론트 파싱·표시는 준비돼 있어도 새로고침하면 사라지므로, 보컬 기능 전체가 BR-47 에 막혀 있다.

## 3. 코드차트 마디별 가사 저장  ⬜ 미시작  (← BR-49)

### 기능 요약
코드 프로젝트(코드차트)의 **마디별 가사**를 저장·반환한다.

### 상황 설명
보컬은 코드차트를 보며 부른다. 프론트는 코드차트에 가사 표시·편집을 이미 붙였다(마디 아래 절별 한 줄, 수정 모드에서 직접 입력). 그런데 **저장할 곳이 없다.**

악보(BR-47)와 달리 코드차트는 **음표가 없다** — 음절을 음에 붙일 수 없으므로 데이터 모델이 다르다:
- 악보: `notes[].lyrics` (음절 단위, `syllabic`·`extend` 포함)
- 코드차트: `bars[].lyrics: string[]` (**마디 단위 텍스트**, 절별 한 줄)

현재 코드차트 저장 스키마는 이렇게 얇다(실측):

| 스키마 | 필드 |
|---|---|
| `ChordProjectUpdateRequest` | `key`, `title` |
| `ChordProjectCreateRequest` | (가사 없음) |
| `ChordEntryRequest` | `bar`, `beat`, `symbol` |
| `AddChordsRequest` | `progression` |

**5개 스키마 전부 `lyrics` 없음**을 OpenAPI 로 확인했다.

### 기능 상세
- **사용자**: 보컬·일반 사용자(코드차트 작성·열람)
- **권한**: 로그인 필요(본인/관리자)
- **시나리오**: 코드차트 수정 모드 → 마디 아래 칸에 가사 입력 → 저장 → 다시 열어도 유지
- **동작 조건**:
  - `제안` — 마디 단위로 가사를 받는다. 코드가 `bar` 인덱스로 저장되므로 같은 축을 쓴다:
    ```jsonc
    // 예) 1마디 1절 "Beau-ti-ful love," / 2절 "love, I've roamed"
    "lyrics": [ { "bar": 1, "verse": 1, "text": "Beau-ti-ful love," },
                { "bar": 1, "verse": 2, "text": "love, I've roamed" } ]
    ```
    · `bar` 1부터 · `verse` 1부터 · `text` 문자열(빈 문자열이면 그 절 삭제)
  - 저장 위치는 백엔드 판단(코드 엔트리와 같은 테이블/별도 테이블 무방). 프론트는 **마디×절 → 문자열** 만 왕복되면 된다.
  - 목록에서 걸러야 하면 BR-48 과 같은 `hasLyrics` 플래그를 코드 프로젝트에도.
- **검증 조건**: 가사를 넣은 코드차트를 저장 → `GET` 으로 되받아 마디·절·문자열이 동일한지.
- **기대 결과 및 완료 기준**:
  - [ ] 코드 프로젝트 저장/조회에 마디별 가사 포함
  - [ ] 절 여러 개 보존(1절·2절…)
  - [ ] 가사 없는 기존 차트는 영향 없음
