## 1. sheet-projects 에 사용자 기보(`sheetData`) 저장  ⬜ 미시작

### 기능 요약
사용자가 에디터로 만들거나 고친 악보를 자기 `내 악보 차트`에 저장한다.

### 상황 설명

**왜 지금 막혔는가.** 에디터(`/editor`)는 원래 어드민 도구여서 저장 목적지가 넷 다 **사내 수집 DB** 였다 — Solo DB · Lick DB · Comping DB · Lead Sheet DB. 어드민을 스튜디오로 분리하면서 실서비스 에디터에 남는 건 **릭 하나뿐**이 되었다:

| 에디터 타입 | 저장 목적지 | 실서비스에서 |
|---|---|---|
| Lick | `/v1/licks` (사용자 릭) | ✅ 됨 — `내 릭`에서 만들기·수정 |
| Solo | `/v1/solos` (**사내 전역** Solo DB) | ❌ 사용자가 쓰면 안 되는 곳 |
| Comping | 사내 Comping DB | ❌ 어드민 전용 |
| Lead Sheet | 사내 Lead Sheet DB | ❌ 어드민 전용 |

그래서 실서비스 에디터를 **릭 편집 전용**으로 좁혔고(타입 칩 제거·URL 진입 차단), 사이드바의 직접 진입도 없앴다. 남은 구멍이 **내 악보 차트** 다 — 사용자가 악보를 만들거나 고칠 방법이 없다.

**현재 `sheet-projects` 가 담는 것**:
```
publicId · title · composer · performer · keySignature
storageFileIds · omrStatus · omrFailureReason · omrResult(원문 MusicXML)
staffCount · measureCount · tempo
```
`SheetProjectUpdateRequest` 는 `{ title?, key? }` 뿐이다. 즉 **제목과 조성만 고칠 수 있고 음표는 못 고친다.**

프론트는 `omrResult` 를 `omrResultToSheet` 로 `NoteSheetData` 로 바꿔 읽기 전용 뷰어에 그린다. 편집을 지원하려면 그 반대 방향(편집 결과 → 서버)이 필요하다.

**⚠️ MusicXML 로 되돌리는 방식은 권하지 않는다.** 편집 결과를 `omrResult` 에 다시 쓰면 (1) 프론트에 MusicXML 라이터가 없고, (2) OMR 원문이 사용자 편집으로 덮여 재처리·비교가 불가능해진다. **원문(`omrResult`)은 그대로 두고 편집본을 별도 필드로 두는 것**이 맞다.

### 기능 상세
- **사용자**: 로그인한 일반 사용자
- **권한**: 소유자만. `chord-projects` 가 `findAllByUserAndDeletedAtIsNull` 로 좁히는 것과 같은 규칙 — **사내 전역 DB 가 아니다**
- **시나리오**:
  1. `내 악보 차트`에서 `직접 만들기` → 빈 에디터 → 저장 → 내 목록에 생긴다
  2. `내 악보 차트`의 항목에서 `수정` → 에디터에 기보가 채워짐 → 저장 → 같은 항목이 갱신된다
  3. OMR 로 올린 악보를 `수정` → OMR 결과가 채워짐 → 손으로 고쳐 저장 → **원문은 남고** 편집본이 저장된다
- **동작 조건**:

  **필드 추가** — 새 엔드포인트가 아니라 기존 `sheet-projects` 에 얹는 쪽을 제안한다. 목록·삭제·휴지통·폴더가 이미 그쪽에 붙어 있어서, 따로 만들면 프론트가 두 목록을 합쳐야 한다.
  ```
  sheetData    SheetDataRequest/Response?   ← 사용자 편집본. **원문 omrResult 와 별개**
  ```
  - `POST /v1/sheet-projects` 가 `storageFileIds` 없이 `sheetData` 만으로도 생성되어야 한다
    (직접 만들기 = 올린 파일이 없다). 지금은 `storageFileIds` 가 스펙상 필수다
  - `PUT /v1/sheet-projects/{publicId}` 가 `sheetData` 를 받아 **전체 교체**
  - `GET` 응답에 `sheetData` 포함. `null` 이면 프론트는 기존처럼 `omrResult` 를 보여준다
    (편집 한 번도 안 한 OMR 악보)

  **`sheetData` 스키마는 새로 만들 필요가 없다.** `/v1/licks` · `/v1/solos` 가 이미 같은 것을 저장한다 — `measures[].notes[]` 중첩 구조(스키마의 "섹션 4 (sheetData)"). 같은 스키마를 쓰면 프론트가 변환 없이 에디터 출력을 그대로 보내고, 양손 악보(`bassMeasures`)·다중 보표(`staves`)·`accidentalStyle` 도 같은 규칙으로 붙는다.

  ⚠️ **다중 보표(`staves`)를 빠뜨리지 말 것.** 릭·솔로에서 이 필드가 타입 불일치로 문제가 된 적이 있다(문서 `2026-08-08-staves-chordDiagrams-타입불일치`). 같은 실수를 반복하지 않으려면 `staves` 를 처음부터 포함해 주면 좋겠다.

- **검증 조건**:
  - `sheetData` 만으로 생성(파일 없이) → 목록·단건 조회에 나온다
  - 다른 사용자 토큰으로 그 `publicId` 조회 → 404/403 (**소유자 격리**)
  - **왕복 무손실** — 저장 후 되받아 대조: 음표 키·음가·임시표·타이·연음, 코드 심볼,
    양손(`bassMeasures`)·다중 보표(`staves`)·`accidentalStyle`
  - OMR 악보에 `sheetData` 를 저장한 뒤 `omrResult` 가 **그대로 남아 있는가**
  - `PUT` 으로 `title` 만 보낼 때 `sheetData` 가 지워지지 않는가(부분 수정)
- **기대 결과 및 완료 기준**:
  - [ ] 사용자가 자기 악보를 만들고 고쳐 저장할 수 있다
  - [ ] 소유자만 읽고 쓴다
  - [ ] `sheetData` 스키마가 licks·solos 와 같다(`staves` 포함)
  - [ ] `omrResult` 원문이 편집으로 덮이지 않는다
  - [ ] 파일 없이 생성 가능

## 참고 — 프론트가 함께 할 일

백엔드 요청은 아니고 순서 맞추기용 기록.

- `내 악보 차트`에 `직접 만들기` 버튼 + 항목 `수정` 추가 → `/editor` 로 진입
- 에디터의 실서비스 저장 분기를 `sheet-projects` 로 추가(현재는 릭만)
- **이 백엔드가 생기기 전까지는 버튼을 넣지 않는다** — 저장이 안 되는 편집 화면을
  열어 주면 사용자가 작업을 잃는다. 지금은 `내 악보 차트`가 읽기 전용인 채로 둔다

## 우선순위

릭은 몇 마디짜리 짧은 프레이즈여서(8마디 초과는 에디터가 막는다) 곡 단위 악보를
대신할 수 없다.
