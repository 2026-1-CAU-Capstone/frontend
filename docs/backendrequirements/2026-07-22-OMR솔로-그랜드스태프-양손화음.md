## 1. OMR 솔로 — 그랜드스태프(양손·화음) 파싱 보존  🟡 부분 완료  (← BR-32)

### ✅ 완료분 — 코드 심볼 `MeasureInfo.chord` (2026-07-29 확인, 추가 작업 없음)

OMR 코드 인식 결과를 sheetData `measures[].chord` 로 채우는 규칙은 **이미 구현·동작 중**이다. 실호출 sheetData `measures[].chord` = `[null, null, null, "B7", "Gm7  C7", "Fmaj7", …]` — **마디당 2코드는 더블 스페이스**라는 규칙까지 그대로 지켜진다.

- 이어붙이기: `OmrClient.java:654` — `reduce((l, r) -> l + "  " + r)`
- 매핑 키: `OmrClient.java:1184` — `@JsonProperty("musicxml_measure_number")`
- 마디 배정: `MusicXmlParser.java:311-324` `resolveChordFromAssignments()`

### 기능 요약 (남은 범위)
2단(피아노) 악보를 OMR로 파싱할 때, 결과 `sheetData`에 **오른손 = `measures`, 왼손 = `bassMeasures`(낮은음자리표, 1:1 정렬)** 를 채우고, 각 `<chord>` 그룹을 **다중 키 한 음표**(`keys[]`)로 보존한다.

### 상황 설명
입력이 그랜드스태프 폴리포닉 피아노 악보(예: "Blues In F With Comping Voicings" — MusicXML `<staves>2</staves>`, 오른손 `voice 1/staff 1`, 왼손 `voice 5/staff 2`, `<chord>` 다수)인데, 저장된 솔로 sheetData는 **오른손 voice의 최상단 단음만** 남는다. 결과적으로 화면에 단선율 한 줄만 그려지고 왼손·화음이 전부 사라진다.

- **실측(2026-07-22)**: 위 악보(25마디, 화음 135개, `<backup>` 95개)를 프론트 신규 파서로 파싱하니 오른손·왼손 두 보표 + 모든 화음이 정상 복원됨(레퍼런스 구현 존재, 아래). 동일 입력을 라이브 OMR 솔로로 올리면 단선율만 나온다 → **백엔드 파서 단계에서 대보표 구조를 버리는 것**이 원인.
- **미구현 재확인(2026-07-29)**
  - **양손**: `MusicXmlParser` 에 `<staves>`/`<staff>` 분기가 **없다.** 백엔드 java 전체에 `bassMeasures` **0건** — `SheetDataResponse` 에 담을 필드 자체가 없다(→ #21 선행).
  - **화음**: `MusicXmlParser.java:245` 가 `if (hasDirectChild(nEl, "chord")) continue;` 로 화음 구성음을 **명시적으로 버린다.**
  - **OMR 서비스(`/omr`)**: HOMR 출력 보존만 한다. `pipeline/sheet_music_structure.py:158-169` 는 `staves > 1` 이면 단일보표 정리를 건너뛸 뿐, **대보표를 생성하지는 않는다.**
- 프론트 준비 상태: 데이터 모델 `NoteSheetData`에 `bassMeasures`(왼손 파트)·`NoteInfo.keys: string[]`(화음)이 **이미 있고**, 에디터 렌더러는 `bassMeasures` 감지 시 자동으로 2단 대보표를 그린다. 즉 백엔드가 이 형태로만 내려주면 추가 프론트 작업 없이 렌더된다.

### 기능 상세
- **사용자**: 로그인 사용자(피아노/양손 악보 OMR 업로드)
- **권한**: 로그인 필요, 본인 콘텐츠
- **시나리오**: 2단 피아노 악보 이미지 업로드 → OMR → 저장된 솔로를 열면 **오른손·왼손 두 보표 + 화음**이 그대로 보인다
- **동작 조건 (파싱 규칙, `제안`)** — 번호는 원문 유지
  1. 소스 MusicXML이 대보표(파트에 `<staves>2</staves>`, 또는 서로 다른 `<staff>` 번호가 2개 이상)면 **그랜드스태프 모드**로 파싱한다.
  2. `staff 1` 음표 → `measures`(오른손/높은음자리표), `staff 2` 음표 → `bassMeasures`(왼손/낮은음자리표). 두 배열은 **마디 인덱스로 1:1 정렬**(모자라면 빈 마디).
  3. `<chord>` 그룹(첫 `<note>` + 이어지는 `<note><chord/></note>`)은 **한 음표의 `keys[]`** 로 합친다. 키는 **저→고 정렬**, 임시표는 정렬된 키 인덱스 기준으로 부여(`accidentals: { <index>: "#"|"b"|"n"|"##"|"bb" }`).
  4. 시간축은 `<divisions>` 틱으로 추적하되 `<backup>`/`<forward>` 를 반영하고, 각 보표에서 비어있는 구간은 **쉼표로 채워** 마디 박자를 완성한다.
  5. ~~코드 심볼~~ → **✅ 완료** (위 완료분 참조)
  6. 단선율(1단) 악보는 기존과 동일하게 `measures`만 채우고 `bassMeasures`는 비운다(회귀 없음).
  - 응답 계약(참고): 기존 `SoloResponse.sheetData` 스키마에 `bassMeasures`(= `measures`와 동일한 `MeasureInfo[]` 형태)를 추가로 채운다. `MeasureInfo.notes[].keys`는 **배열**이며 화음이면 원소가 여럿이다. ⚠️ 이 필드 추가는 **문서 #21 선행 필요**.
- **검증 조건**

  3. 저장 솔로를 에디터로 열면 2단 대보표로 렌더된다(프론트는 이미 지원).
