# 2026-08-08 · Comping Database 백엔드 부재 + OMR 임시솔로 우회 2건

🏷 **범주(태그):** 콘텐츠·라이브러리·스토리지

Comping Database(스튜디오 `/comping`)는 화면이 완성돼 동작하는데 **백엔드가 없어 데이터가 브라우저 localStorage 에만 남는다.** 브라우저 데이터를 지우면 그대로 사라진다. 그리고 OMR 업로드가 솔로 API 를 빌려 쓰면서 **임시 솔로를 만들고 지우는** 우회를 쓰고 있다.

## 진행 현황
범례: ✅ 완료 · 🟡 진행중 · ⬜ 미시작
- ⬜ 1. Comping 저장소 — 릭·솔로와 같은 결의 CRUD
- ⬜ 2. OMR 결과를 리소스 생성 없이 받는 경로 (임시 솔로 우회 제거)

---

## 1. Comping 저장소 — 릭·솔로와 같은 결의 CRUD  ⬜ 미시작

### 기능 요약
피아노 컴핑 자료를 서버에 저장·조회한다. 릭·솔로가 이미 하는 방식을 그대로.

### 상황 설명
스튜디오의 Comping Database 는 장르별(Swing / Blues / BossaNova / Latin) 수집 도구로 이미 만들어져 있다. Solo Database 와 같은 레이아웃(좌: 장르 사이드바 · 우: 목록 + 악보 미리보기)이고 OMR 업로드·악보 미리보기·삭제가 동작한다.

**다만 저장소가 localStorage 뿐이다.** 코드에도 그렇게 적혀 있다.

```ts
/* Comping Database — **로컬(localStorage) 저장소**.
 * 백엔드는 나중에 붙일 예정이라 지금은 프론트 로컬에만 남긴다.
 * 백엔드가 생기면 이 모듈의 load/save 를 API 호출로 갈아끼우고,
 * 기존 로컬 데이터는 exportCompings() JSON 으로 이관한다. */
const STORAGE_KEY = 'jazzify_comping_entries';
```

화면에도 "백엔드 미구현 — 이 브라우저의 localStorage 에만 저장됩니다" 배지가 붙어 있다.

**왜 문제인가**
- 브라우저 데이터 삭제·시크릿 창·다른 기기 → 데이터가 없다. 릭 153건·솔로 238건과 달리 **백업 대상에서도 빠져 있었다**(2026-08-08 데이터 재고조사 때 서버 DB 만 셌다)
- localStorage 는 약 5MB 다. `sheetData` JSON 을 통째로 담으므로 수십 건이면 한계에 닿는다. 넘치면 조용히 쓰기가 실패한다
- 스튜디오가 별도 도메인으로 배포되면(`jazzifystudio.netlify.app`) **오리진이 달라 기존 로컬 데이터가 안 보인다**

### 기능 상세
- **사용자**: 관리자(내부 스튜디오)
- **권한**: `ADMIN` 또는 `MANAGE` — 릭·솔로 쓰기와 같은 규칙. 실서비스에는 이 화면이 없다
- **시나리오**: 스튜디오에서 컴핑 자료를 등록·조회·삭제 → 기기·브라우저가 바뀌어도 남아 있다
- **동작 조건**:
  - 릭·솔로와 **같은 결**이면 프론트가 그 패턴을 그대로 쓴다. 프론트가 호출할 계약만 `제안`:
    ```
    GET    /v1/compings?genre=SWING&page=0&size=20
    POST   /v1/compings
    GET    /v1/compings/{publicId}
    DELETE /v1/compings/{publicId}
    → { data: { content: [...], totalElements, ... } }   // 기존 페이지 봉투
    ```
  - 지금 프론트가 들고 있는 레코드 모양(그대로 옮기면 이관이 단순해진다):
    ```
    id → publicId (서버 발급)
    title       String
    genre        SWING | BLUES | BOSSA | LATIN     ← 장르가 분류축이다(목록·필터가 이 값으로 묶인다)
    composer     String?
    key          String
    tempo        Integer?
    sheetData    솔로·릭과 같은 sheetData 스키마
    musicXml     String?   ← 원본 MusicXML. 파싱이 놓친 게 있어도 재파싱할 수 있게 보존한다
    createdAt / updatedAt
    ```
  - `genre` 는 enum 으로 두길 제안한다 — 지금 프론트가 4종 고정이고, 오타가 들어오면 목록이 갈라진다
  - `sheetData` 는 솔로와 같은 스키마를 쓰면 좋겠다. 컴핑도 양손 피아노가 기본이라 솔로에서 겪은 왼손·표현정보 유실 문제가 그대로 재현될 수 있다(문서 #33 참조)
  - **기존 로컬 데이터 이관**: 프론트가 `exportCompings()` JSON 을 뜰 수 있다. 벌크 등록 경로가 없으면 한 건씩 POST 로 올린다 — 건수가 적으니 별도 API 는 필요 없다
- **검증 조건**:
  - 등록 후 다른 브라우저(또는 시크릿 창)에서 목록에 보인다
  - `genre=SWING` 필터가 그 장르만 반환
  - 일반 사용자 토큰으로 `GET /v1/compings` → 403
  - 삭제 후 목록·단건 조회에서 사라진다
  - `sheetData` 를 저장 후 되받아 대조 — 양손·화음·표현정보가 그대로인가
- **기대 결과 및 완료 기준**:
  - [ ] 컴핑 CRUD 가 서버에 남는다
  - [ ] `genre` 로 목록 필터
  - [ ] `ADMIN`·`MANAGE` 전용
  - [ ] `sheetData` 왕복 무손실
  - [ ] 기존 로컬 데이터를 올릴 수 있다

## 2. OMR 결과를 리소스 생성 없이 받는 경로  ⬜ 미시작

### 기능 요약
악보 이미지 → MusicXML(또는 파싱된 sheetData) 만 받는 엔드포인트. 지금은 **솔로를 만들었다 지운다.**

### 상황 설명
Comping 화면의 OMR 업로드가 이렇게 동작한다(`CompingPage.tsx`).

```ts
const solo = await createSoloViaOMR(file, {...});   // ① 솔로를 만든다
const st   = await getSoloOmrStatus(solo.publicId); // ② 완료까지 폴링
const full = await getSolo(solo.publicId);          // ③ sheetData 를 꺼낸다
void deleteSolo(solo.publicId).catch(() => {});     // ④ 만든 솔로를 지운다
```

컴핑용 OMR 엔드포인트가 없어서 솔로 것을 빌려 쓴 결과다. 문제:

- **Solo DB 가 오염된다.** ④가 실패하면(네트워크 끊김·탭 종료·403) 컴핑용으로 만든 솔로가 그대로 남는다. `void … .catch(() => {})` 라 실패해도 아무 신호가 없다. 실제로 지금 Solo DB 238건 중 `performer='candidate'` 128건·`Test` 4건처럼 작업 흔적이 섞여 있다
- **OMR 실패가 고아를 만든다.** 생성은 됐고 OMR 이 `FAILED` 로 끝나면 빈 솔로가 남는다(현재 12건이 FAILED 상태다)
- 컴핑이 아닌 다른 용도(미리보기·검수)에도 같은 우회가 필요해질 때마다 반복된다

이건 BR-12(업로드 부분 실패 시 고아 파일)와 같은 뿌리다.

### 기능 상세
- **사용자**: 관리자(내부 스튜디오)
- **권한**: `ADMIN` 또는 `MANAGE`
- **시나리오**: 악보 파일을 올린다 → 인식 결과만 받는다 → 프론트가 확인 후 원하는 리소스로 저장한다(컴핑이든 솔로든)
- **동작 조건**:
  - 프론트가 호출할 계약만 `제안`. 리소스를 만들지 않는 형태:
    ```
    POST /v1/omr/parse        (multipart: file)
    → { data: { jobId } }
    GET  /v1/omr/parse/{jobId}
    → { data: { status: PENDING|PROCESSING|COMPLETED|FAILED,
                progress, musicXml?, failureReason? } }
    ```
  - `musicXml` **원문을 주는 것이 핵심**이다. 지금 OMR 경로는 원문을 안 줘서 컴핑 레코드의 `musicXml` 이 비어 있다(코드 주석에도 그렇게 적혀 있다). 원문이 있으면 파싱을 나중에 개선해도 다시 뽑을 수 있다
  - 결과 보관 기간은 짧아도 된다(받아서 저장하면 끝)
  - 기존 `POST /v1/solos/omr`·`/v1/licks/omr` 는 그대로 둔다 — 그 리소스를 실제로 만들 때는 그게 맞다
- **검증 조건**:
  - 업로드 → 폴링 → `musicXml` 수신. **그 과정에서 Solo·Lick 이 한 건도 생기지 않는다**(총 건수 불변)
  - OMR 실패 → `FAILED` + 사유. 역시 리소스가 생기지 않는다
  - 일반 사용자 토큰 → 403
- **기대 결과 및 완료 기준**:
  - [ ] 리소스를 만들지 않고 OMR 결과만 받을 수 있다
  - [ ] 응답에 `musicXml` 원문이 있다
  - [ ] 프론트가 임시 솔로 생성·삭제 우회를 지울 수 있다
  - [ ] 실패해도 고아 리소스가 남지 않는다
