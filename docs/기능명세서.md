## 1. 제품 개요

Jazzify는 재즈 연주자·학습자를 위한 **코드차트/리드시트 분석 + AI 화성학 튜터 + 백킹트랙 연습** 통합 플랫폼이다.

| 핵심 가치 | 내용 |
| --- | --- |
| **분석** | 1,460곡 표준 + 사용자 차트를 ii-V-I·세컨더리 도미넌트·모달 인터체인지로 자동 분석·시각화 |
| **AI 튜터** | RAG 채팅으로 출처(유튜브 딥링크) 달린 답변 + DB 릭 추천 |
| **연습** | 풀밴드 자동 반주(콤핑+워킹베이스+드럼, 13장르), 12키 릭 연습, 구간 루프 |
| **자료화** | OMR로 이미지 악보 디지털화, 릭/솔로 DB(WJazzD 8,000+) 검색 |

**플랫폼**: 웹(데스크톱/태블릿) + iOS 네이티브(Capacitor) · HashRouter SPA

## 2. 시스템 아키텍처

### 2.1 기술 스택

| 계층 | 기술 |
| --- | --- |
| 프론트 | React 19, Vite 8(rolldown), styled-components 6, TypeScript strict |
| 악보 렌더 | VexFlow 5, OSMD |
| 오디오 | Web Audio API, smplr(사운드폰트), 자체 백킹 엔진 |
| 네이티브 | Capacitor 8 (iOS) |
| 백엔드 | Jazzify API — JWT(access) + HTTP-only refresh 쿠키(RTR) |
| AI | Anthropic Claude (백엔드 프록시 + RAG / 클라 직접 폴백) |
| OMR | 백엔드 OMR (이미지→MusicXML→코드/멜로디) |
| RAG | 백엔드 RAG (멀티쿼리 + RRF + 유튜브 딥링크 출처) |

### 2.2 구성도

```
┌────────────── 클라이언트 (Web / iOS) ──────────────┐
│ React SPA (HashRouter)                              │
│  ├─ 페이지 18 · 컴포넌트 도메인 9 · 전역 Provider     │
│  ├─ 재생 엔진(FE): 백킹·사운드폰트·스윙·카운트인       │
│  ├─ OMR 원본 이미지 캐시(FE): IndexedDB              │
│  └─ API 클라 13모듈 (authFetch: Bearer + refresh)   │
└──────┬───────────────────┬──────────────────┬──────┘
       │                   │                  │
 [Jazzify 백엔드]    [Anthropic API]   [localStorage/IndexedDB]
 jazzify.p-e.kr/api  api.anthropic.com 토큰·캐시·OMR이미지
  ├ 인증(RTR)        (클라 직접 폴백)
  ├ 채팅 스트림 + RAG
```

## 6. 수정 필요 (Known Defects)

### ✅ 신규 — 2026-07-21 에디터 꾸밈음(acciaccatura) 생성

에디터 툴바에 꾸밈음 입력 모드(작은 슬래시 음표 아이콘) 추가 — ON이면 피아노/삽입 입력이 슬래시 꾸밈음으로 생성. 음표 편집 창의 토글도 슬래시(graceSlash)까지 함께 켠다. 에디터 자체 renderSheet가 이제 NoteSheet와 동일하게 GraceNote(작게)+GraceNoteGroup+슬래시로 렌더(기존엔 grace를 정박 실음으로 잘못 그림), voice에서 제외해 마디 길이 불변. 재생은 P-2의 0박 크러시로 이미 동작. vfNotes 1:1 인덱싱 유지(클릭/하이라이트/타이/투플렛 정합).

## 7. 비기능 요구사항 (NFR)

### 7.1 보안

- **시크릿**: `VITE_`는 공개 가능 값 전용. API 키·토큰은 백엔드 보관 필수 (현 위반: C1).
- **인증**: JWT(단기 access, localStorage) + HTTP-only refresh 쿠키 + RTR(재사용 감지 무효화) + 멀티탭 Web Locks.
- **계정 격리**: 로그인/로그아웃 시 사용자범위 캐시 8종·chartEdit prefix·IndexedDB OMR 이미지 정리.
- **CSP**: 외부 스크립트 차단(youtube만)·frame/object 제한 메타. SRI·폰트 셀프호스팅 잔존.
- **에러 노출**: 사용자에겐 `message`만, `detail`은 dev 콘솔만.
- **개선 권고**: access token 메모리/httpOnly화, Anthropic 호출 백엔드 일원화, npm audit 주기 점검.

### 7.2 성능

- **코드 스플리팅**: VexFlow/OSMD(~1.1MB)를 차트/악보 페이지에만 lazy 로드.
- **사운드폰트 캐시**: smplr 샘플 IndexedDB 캐시.
- **재생 정확도**: 백킹은 Web Audio lookahead(200ms). 에디터/12키는 setTimeout 기반(§8 R8 공유훅 단일화).
- **OMR 비동기**: 폴링 + in-flight dedup으로 중복 POST 방지.

### BR-17. 룰엔진이 RAG 런타임에 호출되지 않음 — 질문 시점 화성 분석·모호성 계산 부재 미해결 HIGH BE RAG

| 배경 | BR-3(분리 API)의 **후속**. 홈 채팅에 오디오를 첨부하고 **"피아노만 빼줘" / "MR 만들어줘"** 처럼 말하면 rule-based 인텐트(`lib/stems/intent.ts` — `split`/`extract`/`remove`)가 잡아 인라인 카드(F15.8)로 결과를 준다. |

### BR-30. 공유 링크 — 공개 웹 미배포로 외부 실사용 불가 (BR-2 선결 조건 재확인) 차단 HIGH BE 인프라

| 항목 | 내용 |
| --- | --- |
| 증상 | 공유(F3.16·F4.11)는 코드가 완성·검증됐고 `https://jazzify.app` canonical base 로 링크를 만든다. 그러나 **SPA 가 공개 웹에 미배포**라 외부인이 링크를 열면 아무것도 안 뜬다. (네이티브 origin 이 `capacitor://localhost` 라 죽은 링크가 되던 버그는 수정 완료.) |
| 조치 (인프라) | `jazzify.app`(또는 대체 도메인) 에 **SPA 정적 배포 + SPA fallback 라우팅**(모든 경로 → `index.html`, HashRouter 라 서버 라우팅은 불필요하나 루트는 서빙되어야 함). 배포 전까지 공유 기능은 **내부 테스트 한정**으로 표기할 것. 배포 후 BR-2(토큰 기반 공개 엔드포인트)로 v2 진행. |

### BR-31. 조성(Key) 재해석 결과 서버 영속화 + 서버측 재분석 부재 미해결 MEDIUM BE

| 항목 | 내용 |
| --- | --- |
| 배경 | F3.18(조성 자동 감지·재해석)은 차트에 적힌 조성이 코드 진행과 어긋날 때 교정을 제안한다. **조옮김이 아니라 분석 기준(으뜸조) 교정**이므로 코드 심볼은 불변이고, 도수·다이아토닉·ii-V-I·모달 인터체인지만 다시 계산된다. |
| 증상 | 사용자가 제안을 수락해도 프론트 상태(`sheet.key`)만 바뀐다. **새로고침하거나 다른 기기에서 열면 원래의 틀린 조성으로 되돌아간다.** 코드에 `TODO(backend)` 표시(`ChordPage.tsx::handleApplySuggestedKey`). |
| 프론트가 아직 호출하지 않는 이유 | 클라이언트에는 이미 `updateChordProject(publicId, { title?, key? })` → `PUT /v1/chord-projects/{publicId}` 가 있다. 그러나 아래 **계약 3건이 확인되지 않아** 호출을 붙이지 않았다. 확인/확정되면 프론트 배선은 수 줄이면 끝난다. |
| ❶ 계약 확인 — 키 표기 | **열거형이 서로 다르다.** 백엔드 `CHORD_PROJECT_KEYS` 는 `A_FLAT_MAJOR`·`G_MINOR` 형식(SCREAMING_SNAKE, 이명동음 포함 major 15 + minor 15). 프론트 조성 표기는 `Ab`·`Gm` 형식(피치클래스 기반 12 + 12). **매핑 없이 보내면 400**. 프론트 24키는 전부 백엔드 열거형에 존재하므로 **단방향 매핑표**로 해결 가능. 결정 필요: 매핑을 프론트가 하나, 백엔드가 두 표기를 모두 받나. 또한 응답 필드는 `keySignature` 인데 요청 바디는 `key` 로 **비대칭**이다 — 의도된 것인지 확인. |
| ❷ 계약 확인 — PUT 부분 갱신 | `PUT` 인데 바디에 `{ key }` 만 담긴다. 서버가 PUT 을 **전체 교체**로 처리하면 `title`·`timeSignature` 가 **날아간다**. 필요: 부분 갱신 보장(누락 필드 무시) 또는 `PATCH` 신설. 어느 쪽인지 명시할 것. |
| ❸ 계약 확인 — 캐시 무효화 | 프론트는 `analysisCache` 를 **`project.updatedAt` 버전**으로 무효화한다(`ChordPage.tsx` 의 `getCachedAnalysisEntry`/`setCachedAnalysis`). 조성 변경 시 서버가 **`updatedAt` 을 갱신하지 않으면** 프론트는 **낡은 분석 캐시를 계속 사용**해 변경이 반영되지 않은 것처럼 보인다. 필수: 조성 변경도 `updatedAt` 을 올릴 것. |
| 백엔드 조치 (수용 기준) | <br> ① `key`(조성)를 프로젝트에 **영속화**하고 조회 응답(`keySignature`)에 반영한다.<br><br> ② 변경 시 `updatedAt` 을 갱신한다 (❸ — 없으면 프론트 캐시가 안 깨진다).<br><br> ③ DB 에 적재된 **사전 분석을 새 조성 기준으로 재계산**한다 — `degree`·`functions`·`group_memberships`·`modal_interchange`·`ambiguity_score` 는 모두 **옛 조성 기준**이라 그대로 두면 서버가 내려주는 분석과 실제 조성이 어긋난다. BR-17 의 온라인 분석 API(`POST /v1/analysis/chords`)가 생기면 그대로 재사용 가능.<br><br> ④ 재계산된 분석이 **RAG 의 `chord_context`/`chord_context_text`** 에도 반영되어야 한다(BR-17·BR-18). 안 그러면 AI 튜터가 **틀린 조성 기준으로** 설명한다.<br><br> ⑤ 조성은 공유 링크(F3.16)·PDF 내보내기·백킹 화성 해석에도 **일관되게 전파**되어야 한다.<br> |
| 영향 범위 (정정) | 프론트 **화면은 이미 안전하다** — `analyzeHarmony()` 가 매 렌더마다 `chord.analysis` 를 통째로 재계산해 사전 분석 값을 덮어쓰기 때문이다. 따라서 불일치는 **①영속성(새로고침 시 유실) ②서버가 내려주는 분석 데이터 ③RAG 답변 품질** 세 곳에서만 발생한다. |
| 프론트 임시 대안 (미적용) | 백엔드 조치 전까지 **localStorage 에 조성 오버라이드**를 저장해 새로고침 유실만 막는 스톱갭이 가능하다. 서버 분석·RAG 불일치는 해결되지 않으므로 **기본은 백엔드 조치**. 필요 시 요청. |
